# Day 2 — Disassembling the Intcode program

> A compiler-flavored deep dive into the *problem within the problem*. The
> [function guide](day02_function_guide.md) builds the Intcode VM and notes
> in passing that Part 2 is affine. This file takes the puzzle input apart
> the way you'd take apart an unknown binary: a **linear disassembly**, a
> **dataflow read**, and a **symbolic decompilation** that *proves* the
> affine structure by abstract interpretation rather than asserting it.
>
> Everything here is generated by
> [scripts/intcode_disasm.rkt](../../scripts/intcode_disasm.rkt) — run
> `racket scripts/intcode_disasm.rkt` to reproduce it, or point it at any
> Day 2-style input (`racket scripts/intcode_disasm.rkt path/to/input`).

---

## What we're disassembling

The puzzle input is 145 integers. Treated as Intcode (opcodes `1` add,
`2` multiply, `99` halt; every arithmetic instruction is `op a b dst` and
four cells wide), it disassembles to **36 instructions in a single
straight line** — no branches, because Day 2's instruction set has no jump
opcodes. That's the first structural fact: this is *basic-block-only*
code, one entry, one exit, no control flow. A linear sweep of the
instruction pointer is a complete and correct disassembly (which will stop
being true on Day 5, when jumps arrive — see [Caveats](#caveats-and-day-5)).

Note the disassembler decodes opcodes against the **original** program
bytes, not the running memory. That's legitimate *here* only because no
instruction in this program writes into the address range that later
instructions are fetched from — i.e. the code is not self-modifying along
its own instruction stream. (It *can* be in general; Day 2's worked
example `1,1,1,4,99,...` overwrites its own halt. This input just doesn't,
which is what makes a static disassembly faithful.)

## Pass 2 — Reading the dataflow

Three things jump out once you trace which cell feeds which.

### 1. The first four instructions are dead code

Addresses `0`, `4`, `8`, `12` all write `mem[3]`, and `mem[3]` is **never
read after address 12** — scan the operand columns from address 16 on and
position 3 never appears again. So the entire opening block computes a
value (`mem[3] = noun + verb`, then `+ mem[4]`, then clobbered back to a
constant `2`) that nothing downstream consumes. It is a textbook **dead
store** chain — the kind a compiler's dead-code-elimination pass would
delete outright. AoC's program generator uses position 3 as a scratch cell
and reuses it; the noun/verb that briefly land there at addresses 4–8 are
thrown away at address 12.

The *real* computation starts at address 16, where `noun` (position 1)
first enters the live dataflow via `mem[19] = mem[10] * noun`.

### 2. It's a single linear chain, not a tree

After address 16 the live values form one long dependency chain:

```
mem[19] → mem[23] → mem[27] → mem[31] → mem[35] → mem[39] → mem[43]
       → mem[47] → mem[51] → mem[55] → mem[59] → mem[63] → mem[67]
       → mem[71] → mem[75] → mem[79] → mem[83] → mem[87] → mem[91]
       → mem[95] → mem[99] → mem[103] → mem[107] → mem[111] → mem[115]
       → mem[119] → mem[123] → mem[127] → mem[131] → mem[135] → mem[0]
```

Each step reads the previous result and one *constant* cell (positions 5,
6, 9, 10, 13 — all unmodified program data holding small integers like 1,
2, 3, 4, 5) and writes the next. There is no fan-out, no reconvergence:
it's an accumulator threaded through 31 arithmetic steps. In SSA terms
every value has exactly one use, so the whole thing is a *straight pipe*.

### 3. `noun` and `verb` enter at opposite ends — and that explains B = 1

- **`noun`** enters **early** (address 16) and rides the chain through
  **every multiply**: ×4, ×2, ×3, ×4, ×4, ×2, ×5, ×4, ×2, ×2, ×3, ×2.
  Those multipliers compose to `368640`, so by the end `noun`'s
  coefficient is the full `368640`.
- **`verb`** enters **last** (address 132: `mem[135] = verb + mem[131]`),
  a single addition past every multiply. It never gets scaled, so its
  coefficient is exactly **1**.

This asymmetry is the whole reason Part 2's closed form is so clean:
because `verb`'s coefficient is 1 and `0 ≤ verb ≤ 99 < 368640 = A`, the
target equation `base + A·noun + verb = 19690720` splits by a single
`divmod`: `noun` is the quotient, `verb` is the remainder. The
disassembly *shows* you why the arithmetic the function guide does works.

## Pass 3 — Symbolic decompilation (the proof)

The empirical check in the guide ("I sampled some pairs and they fit a
plane") is suggestive but not a proof. The real proof is **abstract
interpretation**: run the program once, but over the abstract domain of
*affine forms* `c0 + c1·noun + c2·verb` instead of concrete integers.
Seed `mem[1] = noun` (the form `0 + 1·noun + 0·verb`) and `mem[2] = verb`;
every other cell starts as a constant form. Then:

- **add** of two affine forms is always affine (add the coefficients);
- **multiply** is affine **only if at least one operand is a constant**
  form. Two noun/verb-dependent operands would make the result quadratic.

So the abstract interpreter has a built-in failure mode: if it ever hits a
multiply with two non-constant operands, it raises `NONLINEAR` and stops.
**Running to the halt without that failure is a proof that the output is
affine** — there is no path by which a `noun²`, `verb²`, or `noun·verb`
term could have been created.

Here is the full symbolic trace (only the steps whose result depends on
`noun`/`verb` are shown — the constant-folding steps are elided):

```
  [   4] mem[3]   := (noun) + (verb)                  ->  noun + verb
  [   8] mem[3]   := (noun + verb) + (1)              ->  1 + noun + verb
  [  16] mem[19]  := (4) * (noun)                     ->  4·noun
  [  20] mem[23]  := (4·noun) + (1)                   ->  1 + 4·noun
  [  24] mem[27]  := (1 + 4·noun) + (3)               ->  4 + 4·noun
  [  28] mem[31]  := (4 + 4·noun) * (2)               ->  8 + 8·noun
  [  32] mem[35]  := (8 + 8·noun) + (2)               ->  10 + 8·noun
  [  36] mem[39]  := (10 + 8·noun) * (3)              ->  30 + 24·noun
  [  40] mem[43]  := (2) + (30 + 24·noun)             ->  32 + 24·noun
  [  44] mem[47]  := (4) * (32 + 24·noun)             ->  128 + 96·noun
  [  48] mem[51]  := (128 + 96·noun) + (3)            ->  131 + 96·noun
  [  52] mem[55]  := (131 + 96·noun) + (2)            ->  133 + 96·noun
  [  56] mem[59]  := (133 + 96·noun) + (2)            ->  135 + 96·noun
  [  60] mem[63]  := (135 + 96·noun) * (4)            ->  540 + 384·noun
  [  64] mem[67]  := (2) + (540 + 384·noun)           ->  542 + 384·noun
  [  68] mem[71]  := (2) * (542 + 384·noun)           ->  1084 + 768·noun
  [  72] mem[75]  := (1084 + 768·noun) + (1)          ->  1085 + 768·noun
  [  76] mem[79]  := (5) * (1085 + 768·noun)          ->  5425 + 3840·noun
  [  80] mem[83]  := (4) + (5425 + 3840·noun)         ->  5429 + 3840·noun
  [  84] mem[87]  := (1) + (5429 + 3840·noun)         ->  5430 + 3840·noun
  [  88] mem[91]  := (5430 + 3840·noun) * (4)         ->  21720 + 15360·noun
  [  92] mem[95]  := (1) + (21720 + 15360·noun)       ->  21721 + 15360·noun
  [  96] mem[99]  := (21721 + 15360·noun) * (2)       ->  43442 + 30720·noun
  [ 100] mem[103] := (43442 + 30720·noun) + (2)       ->  43444 + 30720·noun
  [ 104] mem[107] := (43444 + 30720·noun) * (2)       ->  86888 + 61440·noun
  [ 108] mem[111] := (86888 + 61440·noun) * (3)       ->  260664 + 184320·noun
  [ 112] mem[115] := (260664 + 184320·noun) + (1)     ->  260665 + 184320·noun
  [ 116] mem[119] := (260665 + 184320·noun) + (2)     ->  260667 + 184320·noun
  [ 120] mem[123] := (2) * (260667 + 184320·noun)     ->  521334 + 368640·noun
  [ 124] mem[127] := (1) + (521334 + 368640·noun)     ->  521335 + 368640·noun
  [ 128] mem[131] := (521335 + 368640·noun) + (5)     ->  521340 + 368640·noun
  [ 132] mem[135] := (verb) + (521340 + 368640·noun)  ->  521340 + 368640·noun + verb

```

The recovered closed form:

```
output(noun, verb) = 521344 + 368640·noun + verb
                     ^base    ^A             ^B
```

Every multiply in the trace has a **constant** on at least one side (look
at the `[28] * (2)`, `[44] (4) *`, `[120] (2) *` steps — the variable
operand is always paired with a literal). The interpreter never raised
`NONLINEAR`, so the program is *provably* affine on this input. `base`,
`A`, `B` match the three concrete probe runs the guide used
(`run-with 0 0`, `run-with 1 0`, `run-with 0 1`) exactly — the symbolic
run computes all three coefficients in a *single* pass instead of three.

### The decompiled program, in one line

After dead-code elimination and constant folding, the entire 145-cell
program is:

```
mem[0]  =  521344  +  368640 * noun  +  verb
```

Set `noun = 12, verb = 2` (Part 1): `521344 + 368640·12 + 2 = 4945026`. ✓
Solve `… = 19690720` (Part 2): `noun = 52, verb = 96`, answer `5296`. ✓

## The compiler connection

What the disassembler does has proper names in the literature, and they're
worth attaching because they transfer:

- **Abstract interpretation** (Cousot & Cousot, 1977): execute a program
  over an *abstract domain* that over-approximates concrete values, to
  prove a property without enumerating inputs. Here the abstract domain is
  "affine forms over `{noun, verb}`," and the property is "the output is
  affine." The brute force tries 10,000 concrete points; abstract
  interpretation establishes the same fact in one symbolic pass.
- **Affine-relation analysis** — the specific domain. Tracking exact
  linear relationships among program variables is **Karr's algorithm**
  (1976); it's the affine-equalities domain in modern static analyzers.
  Our case is the easy slice of it: straight-line code, two symbols, no
  joins (because no branches).
- **Constant folding + dead-code elimination**: the disassembler's
  observation that addresses 0–12 are dead, and that 31 chained ops
  collapse to one affine expression, is exactly what an optimizing
  compiler's DCE and constant-propagation passes would do to this basic
  block. The "one-line decompilation" is the fully-optimized form.
- **Symbolic execution**: seeding inputs as symbols and propagating
  expressions is the technique behind tools like KLEE. The difference is
  that symbolic execution generally keeps *full* expressions (and forks at
  branches); we keep only the affine *abstraction*, which is cheaper and,
  on branchless affine code, lossless.

The clox parallel: this is what a constant-folding peephole optimizer over
clox bytecode would do to a chunk that only `OP_ADD`/`OP_MULTIPLY`s
compile-time-known operands — fold the whole basic block to one
`OP_CONSTANT`. The only twist is that two operands (`noun`, `verb`) are
*symbolic* rather than constant, so the fold lands on an affine expression
instead of a single number.

## Caveats and Day 5

This disassembler is deliberately Day-2-shaped, and it will need work for
the rest of the Intcode trilogy:

- **Jumps (Day 5).** Opcodes 5/6 (`jump-if-true`/`jump-if-false`) break
  the linear sweep: the next instruction is no longer `ip + width`, and
  decode order stops matching address order. A correct disassembler then
  needs **recursive-descent / control-flow-following** decoding (start at
  entry, follow each branch target), the standard answer to the "linear
  sweep vs. recursive traversal" disassembly dichotomy.
- **Parameter modes (Day 5).** Immediate vs. position mode changes how
  each operand is decoded — the disassembler must read the mode digits
  from the opcode (`ABCDE`: `DE` = opcode, `C`/`B`/`A` = parameter modes)
  before it can print operands correctly.
- **Affinity stops being free.** With data-dependent jumps, the output is
  no longer a single affine form — the abstract interpreter would have to
  *join* affine forms at control-flow merge points (the lattice join in
  Karr's algorithm), and a branch on a noun/verb-dependent value
  generally destroys affinity altogether. Day 2's closed form is a luxury
  of branchless code.

When Day 5 lands and the VM gets extracted into `src/intcode.rkt`, this
script is the natural seed for a `tools/`-grade disassembler that grows
the same way the VM does.
