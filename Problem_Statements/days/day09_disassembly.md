# Day 9 — Disassembling the BOOST program

> The [function guide](day09_function_guide.md) finishes the Intcode machine
> by adding **relative mode** and the **relative base** (opcode `9`), and
> notes in passing that Part 2 "does real algorithmic work behind the single
> input branch — the self-test was just the warm-up." This file takes the
> BOOST program apart and shows *what that work is*. The headline is a clean
> inversion of [Day 5](day05_disassembly.md): BOOST is **not self-modifying**
> and its jumps use static targets, so recursive-descent disassembly — which
> died after two instructions on Day 5 — here recovers **essentially the whole
> program**. And the thing it recovers is the most architecturally literate
> input in the trilogy: a **recursive subroutine that uses the relative base
> as a stack frame pointer**, called the slowest possible way. The new feature
> Day 9 added isn't a curiosity — it's a *calling convention*.
>
> Generated by [scripts/intcode_disasm.rkt](../../scripts/intcode_disasm.rkt) —
> run `racket scripts/intcode_disasm.rkt inputs/day09.txt` to reproduce.

---

## What we're disassembling

The puzzle input is **973 integers**. Two features arrived on Day 9, and both
change the disassembler:

1. **Relative mode (parameter mode `2`).** An operand can now name
   `mem[rb + k]` — a cell *offset by a movable relative base* `rb`. The
   decoder gains a third operand rendering, `rel[k]`, alongside `#k`
   (immediate) and `mem[k]` (position). Crucially, **writes** can be relative
   too, so `render-write` becomes mode-aware for the first time.
2. **Opcode `9` (adjust relative base).** `9 p` does `rb += p`. The executor
   gains a `base` accumulator threaded beside `ip`, exactly as the
   [function guide](day09_function_guide.md) describes. In the disassembly it
   prints as `REL_BASE += …`.

These are precisely the two extensions the
[Day 5 disassembly's "Caveats and Days 7 / 9" section](day05_disassembly.md)
predicted: *"a third parameter mode (`2`) and a movable base register join
`param-mode`; the decoder gains a `rel[k]` operand rendering and the executor
a `base` accumulator. The histogram-and-trace structure is unchanged."* It is.

## Pass 1 — Static recursive descent (and why it *works* this time)

On [Day 5](day05_disassembly.md) recursive descent decoded **two**
instructions before self-modifying code defeated it; on
[Day 7](day07_disassembly.md) it managed **three** before an operand-overlap
jump went data-dependent. On Day 9 it decodes **305 instructions covering the
entire 973-cell program** — start to finish, with only two cells (`63`, `64`,
the scratch/accumulator pair) left as data. Following control flow from
address 0 simply *works*, because BOOST:

- **never rewrites a cell it later executes** (no self-modification), and
- **uses immediate jump targets** for all its structural control flow (the
  only data-dependent jumps are the `jump rel[k]` returns at the very end,
  and the linear fall-through scan of each test block reaches their targets
  anyway).

So this is the one Intcode program in the trilogy where the static, on-disk
disassembly is *faithful*. The dynamic trace (Pass 2) is still worth running —
it's how we measure relative-mode usage and the Part 2 blow-up — but it
confirms the static picture rather than rescuing it. The head of the program:

```
addr | raw                      | operation
-----+--------------------------+-------------------------------------
   0 | 1102 34463338 34463338 63 | mem[63] = #34463338 * #34463338
   4 | 1007 63 34463338 63      | mem[63] = (mem[63] < #34463338)
   8 | 1005 63 53               | if mem[63] != 0 jump #53
  11 | 1101 3 0 1000            | mem[1000] = #3 + #0
  15 | 109 988                  | REL_BASE += #988
  17 | 209 12                   | REL_BASE += rel[12]
  19 | 9 1000                   | REL_BASE += mem[1000]
  21 | 209 6                    | REL_BASE += rel[6]
  23 | 209 3                    | REL_BASE += rel[3]
  25 | 203 0                    | rel[0] = INPUT
  27 | 1008 1000 1 63           | mem[63] = (mem[1000] == #1)
  31 | 1005 63 65               | if mem[63] != 0 jump #65
  34 | 1008 1000 2 63           | mem[63] = (mem[1000] == #2)
  38 | 1005 63 904              | if mem[63] != 0 jump #904
  41 | 1008 1000 0 63           | mem[63] = (mem[1000] == #0)
  45 | 1005 63 58               | if mem[63] != 0 jump #58
  …
```

Three regions fall out, and the rest of this file is one section each:

| Region | Addresses | Role |
|--------|-----------|------|
| **Compliance self-test** | `0 .. 25` | Prove the VM is complete (bignums + relative mode), then read the mode input |
| **Input dispatcher** | `27 .. 47` | Branch on input `1` / `2` / `0` |
| **Test battery** | `65 .. 903` | Compute the keycode as a self-checking shift-and-add checksum (input `1`) |
| **Boost computation** | `904 .. 970` | A recursive subroutine on a relative-base stack frame (input `2`) |

## The compliance self-test, cell by cell (`0 .. 25`)

This 26-cell prologue is the whole reason the puzzle prose insists on "support
for large numbers" and "a complete Intcode computer." It is two checks
back-to-back.

### The bignum check (`0 .. 8`)

| Addr | Instruction | Effect |
|-----:|-------------|--------|
| 0 | `mem[63] = #34463338 * #34463338` | Square a constant. `34463338² = 1187724635522244` — a **16-digit** number that overflows 32 bits (and even just clears 50 bits). |
| 4 | `mem[63] = (mem[63] < #34463338)` | Is the product *smaller* than the multiplicand? On a correct (arbitrary-precision) machine: **no** → `0`. On a 32-bit machine the product wraps to a small value → `1`. |
| 8 | `if mem[63] != 0 jump #53` | If the product came out wrong, branch to the **fault handler** at `53` (which emits a diagnostic and halts). |

This is a multiply-then-compare **overflow detector**. Racket integers are
bignums, so `mem[63]` is `0` and the jump is not taken — the
[function guide](day09_function_guide.md) calls this "big numbers for free."
A fixed-width VM that used `i32` cells fails right here, at the second
instruction.

### The relative-mode warm-up (`11 .. 25`)

The next cells are a tiny, self-checking exercise of opcode `9` and relative
reads, walking `rb` from `988` up to exactly `1000`:

| Addr | Instruction | `rb` after | Reasoning |
|-----:|-------------|-----------:|-----------|
| 11 | `mem[1000] = #3` | — | Seed a sentinel: `mem[1000] = 3`. |
| 15 | `REL_BASE += #988` | `988` | Immediate base set. |
| 17 | `REL_BASE += rel[12]` | `991` | `rel[12] = mem[988+12] = mem[1000] = 3`. |
| 19 | `REL_BASE += mem[1000]` | `994` | Position read of the same `3`. |
| 21 | `REL_BASE += rel[6]` | `997` | `rel[6] = mem[994+6] = mem[1000] = 3`. |
| 23 | `REL_BASE += rel[3]` | `1000` | `rel[3] = mem[997+3] = mem[1000] = 3`. |
| 25 | `rel[0] = INPUT` | `1000` | `rel[0] = mem[1000+0] = mem[1000] = INPUT`. |

Every step that touches `rel[k]` only lands on the right cell if relative mode
computes `mem[rb + k]` correctly *and* opcode `9` has been moving `rb` exactly
as instructed — three increments of `3` from `988` must reach `1000` so that
`rel[0]` aliases `mem[1000]`. The warm-up **is** the relative-mode unit test,
and its payload is "read the diagnostic input (1 or 2) into `mem[1000]`."

This is also why the function guide notes Day 9 is "the first day that
*needs*" the grow-on-write memory: `mem[1000]` is far past the loaded image,
and `rb` will roam over a high scratch region throughout.

## The input dispatcher (`27 .. 47`)

```
  27 | mem[63] = (mem[1000] == #1)   ;; input == 1 ?
  31 | if mem[63] != 0 jump #65      ;;   → test battery
  34 | mem[63] = (mem[1000] == #2)   ;; input == 2 ?
  38 | if mem[63] != 0 jump #904     ;;   → boost computation
  41 | mem[63] = (mem[1000] == #0)   ;; input == 0 ?
  45 | if mem[63] != 0 jump #58      ;;   → "echo" diagnostic
  48 | OUTPUT mem[25] / OUTPUT #0 / HALT   ;; unrecognized input
```

Same *role* as [Day 5](day05_disassembly.md)'s system-ID dispatch — the input
selects which battery runs — but a different *mechanism*. Day 5 folded the
input into an opcode by arithmetic (`mem[6] = input + 1100`), a self-modifying
trick that defeated static analysis. Day 9 dispatches with **three plain
`equals` + `jump-if-true` pairs**, fully visible on disk. The puzzle has
stopped obfuscating the dispatcher; the interest has moved to what the
branches *do*. There are three fault/diagnostic exits — `48`, `53`
(the bignum-failure handler from address 8), and `58` — each emitting a small
value and halting; on a correct machine running input `1` or `2`, none are
reached.

The canonical name is the same as Day 7's: a **dispatch on the input**, here a
small `if/else-if` ladder rather than a jump table.

---

## The test battery (`65 .. 903`) — a self-checking keycode

Input `1` lands at `65`. The first ~30 instructions (`65 .. 181`) are pure
setup: they splatter constants into a **register file** at `mem[1000 .. 1029]`
(e.g. `mem[1023] = 344`, `mem[1013] = 26`, `mem[1005] = 24`, …). Then `185`
onward is a long chain of near-identical **test blocks**, each shaped like:

```
 185 | REL_BASE += …              ;; reposition the frame for this test
 187 | mem[63] = (#35 == rel[8])  ;; a comparison against the register file
 191 | if mem[63] != 0 jump 201   ;; pass/fail branch
 194 | mem[64] = mem[64] + #1     ;;   set the low bit
 198 | jump 203
 201 | OUTPUT mem[187]            ;;   failure-diagnostic exit (emits a code)
 203 | mem[64] = mem[64] * #2     ;; shift the accumulator left
```

The accumulator `mem[64]` is a **shift register**: every block does
`mem[64] *= 2` (shift left one bit) and conditionally `mem[64] += 1` (set the
low bit), so across the ~37 blocks it builds a specific integer one bit at a
time. The genius is that each "bit" is gated on a relative-mode read, a
comparison, and a base adjustment all behaving *exactly* to spec — get any of
them wrong and a different bit lands, and the final number is garbage. The
`OUTPUT mem[…]` arms are **failure diagnostics**: on a broken VM one of them
fires early and emits the address of the test that didn't behave; on a correct
VM they're all skipped and the single output is the finished accumulator.

So the **BOOST keycode `4080871669` is a checksum of correct VM behavior** —
the same idea as Day 5's TEST diagnostic ("every test reports success"),
compressed into one self-validating number. The dynamic trace confirms input
`1` emits *exactly one* value and runs only **209 instructions**: the
self-test is cheap because it's a fixed straight-ish walk, not a computation.

## The boost computation (`904 .. 970`) — recursion on a relative-base stack

This is the payoff, and the reason Day 9's feature exists. Input `2` lands at
`904`:

```
 904 | rel[1] = #27               ;; argument n = 27
 908 | rel[0] = #915              ;; return address
 912 | jump #922                  ;; CALL the subroutine at 922
 915 | rel[1] = rel[1] + #53897   ;; result += 53897
 919 | OUTPUT rel[1]              ;; emit the distress coordinate
 921 | HALT
```

`922` is a **subroutine** that, read with an architect's eye, has a textbook
**prologue / body / epilogue** shape:

```
 922 | REL_BASE += #3             ;; PROLOGUE: push a stack frame (rb += frame size)
 924 | mem[63] = (rel[-2] < #3)   ;; if n < 3 …
 928 | if mem[63] != 0 jump #964  ;;   … base case
 931 | rel[1] = rel[-2] + #-1     ;; arg = n - 1
 935 | rel[0] = #942              ;; return address
 939 | jump #922                  ;; CALL T(n-1)
 942 | rel[-1] = rel[1]           ;; save T(n-1) into a local
 946 | rel[1] = rel[-2] + #-3     ;; arg = n - 3
 950 | rel[0] = #957              ;; return address
 954 | jump #922                  ;; CALL T(n-3)
 957 | rel[-2] = rel[1] + rel[-1] ;; return value = T(n-3) + T(n-1)
 961 | jump #968
 964 | rel[-2] = rel[-2]          ;; BASE CASE: return value = n
 968 | REL_BASE += #-3            ;; EPILOGUE: pop the stack frame (rb -= frame size)
 970 | jump rel[0]                ;; RETURN to the saved address
```

Read the relative-mode operands as **stack slots relative to a frame
pointer** and the whole thing decodes as a compiled function:

| Slot | Role | x86 analogue |
|------|------|--------------|
| `rel[-2]` | the argument `n` / the return value | `[rbp - 16]` |
| `rel[0]` | the **return address** | the pushed return IP |
| `rel[1]`, `rel[-1]` | locals (`arg`, saved sub-result) | `[rbp + 8]`, `[rbp - 8]` |
| `rb` itself | the **frame pointer** | `rbp` |

The calling convention is explicit in the opcode-`9` pairs:
`REL_BASE += #3` on entry **pushes a frame**, `REL_BASE += #-3` on exit
**pops** it, and `jump rel[0]` is `ret`. Caller and callee agree on the frame
size (`3`), so a child's `rel[-2]` is the slot the parent wrote as `rel[1]` —
that overlap *is* the argument-passing protocol. **This is exactly why the
puzzle demands a "complete" computer:** position mode hard-codes absolute
addresses and cannot give two live invocations of the same code their own
locals; relative mode makes the subroutine **relocatable**, which is the
precondition for recursion. BOOST isn't testing a feature for its own sake —
it's *running compiled code that needs a stack*.

### What it computes

The recurrence is

```
T(n) = n                       for n < 3
T(n) = T(n-1) + T(n-3)         otherwise
```

called at `n = 27`, with `+ 53897` added to the result. Verified in Python
([the same shape as python/day09.py](../../python/day09.py)):

```
T(27)            = 21305
T(27) + 53897    = 75202        ← the Part 2 answer
naive call count = 37119
```

It's a **tribonacci-flavored tree recursion** (`T(n-1) + T(n-3)`) evaluated
with **no memoization** — the single slowest correct method. That is the whole
explanation for the [function guide](day09_function_guide.md)'s "Part 2 is
~530× Part 1" benchmark row: Part 1 walks a fixed 209-instruction self-test;
Part 2 unfolds an exponential-ish call tree of **37,119 invocations**.

### The trace ties out to the unit

The dynamic histogram for input `2` makes the calling convention *countable*:

```
=== DYNAMIC TRACE — input 2 (sensor-boost mode) ===
371205 instructions executed.
      74243  adjust-rel-base (9)
  relative-mode reads  : 185597
  relative-mode writes : 129918
  single output         : 75202
```

Each call executes exactly **two** opcode-`9`s (one prologue push, one
epilogue pop), so the frame traffic should be `2 × 37119 = 74238`, plus the
**5** base adjustments in the compliance warm-up (`988`, then three `+3`
steps, plus the `9 1000` position-mode one) → **74243**. The trace reports
`74243` opcode-`9`s **to the unit**. There is no cleaner confirmation that
"the relative base is a stack pointer" than watching it push and pop once per
function call, 37,119 times.

## Pass 2 — the two diagnostic modes, side by side

```
=== DYNAMIC TRACE — input 1 (test mode) ===
209 instructions executed.
         40  add (1)        54  mul (2)         1  in (3)        1  out (4)
         41  jt (5)          9  jf (6)          7  lt (7)       19  eq (8)
         37  adjust-rel-base (9)               1  halt (99)
  relative-mode reads  : 27      relative-mode writes : 9
  single output        : 4080871669

=== DYNAMIC TRACE — input 2 (sensor-boost mode) ===
371205 instructions executed.
      92798  add (1)     37121  mul (2)         1  in (3)        1  out (4)
     111360  jt (5)      18559  jf (6)      37120  lt (7)        2  eq (8)
      74243  adjust-rel-base (9)               1  halt (99)
  relative-mode reads  : 185597  relative-mode writes : 129918
  single output        : 75202
```

The two columns are the entire story of the day:

- **Both modes use relative mode** — input `1` does 27 relative reads / 9
  writes, input `2` does 185,597 / 129,918. The self-test exercises the
  feature lightly to *certify* it; the boost path leans on it as a stack and
  hammers it. Either way, a VM that skipped mode `2` produces wrong output,
  not an error — which is exactly the failure BOOST is built to catch.
- **The ~1,776× instruction ratio** (`371205 / 209`) is the same fact as the
  function guide's ~530× wall-clock ratio, just measured in instructions
  rather than milliseconds (the per-instruction cost differs between the
  idiomatic VM and this tracer). Both say the same thing: **the self-test is a
  warm-up; the boost is a real, unmemoized recursion.**
- **`eq (8)` collapses from 19 to 2.** The test battery is comparison-heavy
  (it's all `==` checks against the register file); the recursion uses almost
  none — its branching is the single `<` base-case test, run once per call
  (`lt = 37120 ≈ 37119`).

## The problem within the problem

Day 9's prose is about a *feature* (relative mode); the disassembly reveals
the feature is a *calling convention*, and Part 2 is **a function call**.

| Layer | What the puzzle says | What the program is |
|-------|----------------------|---------------------|
| **Outer** | "Add relative mode, run BOOST" | Implement base-plus-displacement addressing |
| **Middle** | "Test mode emits a keycode" | A self-checking checksum of correct VM behavior |
| **Inner** | "Boost mode emits coordinates" | `T(n)=T(n-1)+T(n-3)` at `n=27`, on a relative-base stack |

We never have to *understand* the recurrence to solve the puzzle — the VM
executes it for us, which is the recurring AoC-2019 lesson that the
[function guide](day09_function_guide.md) frames as "BOOST is hiding a real
algorithm we never have to understand, only execute." The disassembly is how
you find out it was a recursive function the whole time. Contrast the trilogy:

- **[Day 5](day05_disassembly.md):** the obfuscation *was* the input
  (self-modifying opcode dispatch). Static analysis defeated; the meta-problem
  is "what does the self-test test."
- **[Day 7](day07_disassembly.md):** a plain jump table; the meta-problem is
  the **amplifier topology** Part 2 imposes, not the bytecode.
- **Day 9:** no obfuscation at all — the bytecode is honest compiled code. The
  meta-problem is that the honest code is a **naive recursion**, and the
  "feature" the day adds is the **stack discipline** that makes recursion
  expressible.

## Architecture & disassembly-theory connections

- **The relative base is a frame pointer.** `rb` is `rbp`/the base pointer;
  relative mode is **base-plus-displacement addressing** (`[rbp + disp]`, the
  workhorse mode of every stack machine). `REL_BASE += k` / `REL_BASE += -k`
  bracketing a subroutine is a **function prologue / epilogue**. Once you see
  this, every `rel[k]` reads as a named local or argument, and the
  disassembly stops being Intcode and starts being a stack frame.
- **`jump rel[0]` is `ret`.** Storing a return address in a frame slot and
  jumping through it is the call/return protocol; the only reason it needs
  relative mode is so each invocation has *its own* `rel[0]`. Position mode
  would force a single global return slot — fine for a leaf call, fatal for
  recursion.
- **Naive tree recursion** (`T(n-1) + T(n-3)`, no memo) is the canonical
  source of exponential blow-up — the same shape as naive Fibonacci. The fix,
  if the puzzle asked us to *write* it, is memoization or bottom-up DP
  (`O(n)`); the puzzle instead asks us only to *run* it, so the slow version
  is the intended cost.
- **Recursive descent finally succeeds** (cf. the Day 5 file's three-strategy
  taxonomy) because BOOST violates none of its assumptions: no
  self-modification, static branch targets. It's the control case that shows
  why the earlier days' programs were specifically constructed to break static
  analysis — and that AoC stopped doing so once the puzzle's interest moved
  from "resist disassembly" to "hide an algorithm in plain sight."

**Rust analogue.** The boost subroutine is, transparently:

```rust
fn t(n: i64) -> i64 {
    if n < 3 { n } else { t(n - 1) + t(n - 3) }   // its own stack frame per call
}

fn main() {
    println!("{}", t(27) + 53897);   // 75202
}
```

The Intcode is a bytecode encoding of exactly this, with the relative base
playing the role the CPU's `rsp`/`rbp` play for `t`'s activation records. The
[function guide's Rust section](day09_function_guide.md) shows the *interpreter*
in Rust; this is the *program the interpreter runs*, in Rust — and it's four
lines, because all the machinery the disassembly exposes (the frame pushes,
the return-address slots, the argument overlap) is what the compiler generates
for you from those four lines.
