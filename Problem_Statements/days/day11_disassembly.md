# Day 11 — Disassembling the hull-painting robot

> The [function guide](day11_function_guide.md) builds `paint-hull` to drive
> the robot's program with a live camera feed because the program's inputs
> can't be known ahead of time — each one depends on where the robot's own
> prior output has already moved it. This file takes that program apart, and
> the headline finding is sharper than "same trick as Day 5/7's self-mod
> code": **the very first camera reading is a one-time fork that routes
> execution into one of two almost entirely disjoint programs living in the
> same 659 cells.** Start on black (Part 1) and the machine spends its whole
> run in a self-modifying, non-recursive prologue that never once touches
> relative mode. Start on white (Part 2) and it jumps immediately into a
> completely different relative-base **recursive engine** — real
> call/return via a computed `jump rel[0]`, the same calling-convention idea
> [Day 9](day09_disassembly.md)'s BOOST program used, but here with
> genuinely dynamic return addresses that static descent can't resolve.
> Static disassembly gets most of both halves; the interactive dynamic trace
> — the one static input lists can't drive — gets the rest, and reproduces
> both real answers (`2129` and `PECKRGZL`) as a side effect of merely
> tracing.
>
> Generated by [scripts/intcode_disasm.rkt](../../scripts/intcode_disasm.rkt) —
> run `racket scripts/intcode_disasm.rkt inputs/day11.txt` to reproduce.

---

## What we're disassembling

The puzzle input is **659 integers**. Day 11's program is the first the
disassembler has met that takes **interactive** input: every value opcode 3
reads is a camera reading of whatever panel the robot is currently
standing on, and the robot is only standing there because of every
`(paint, turn)` pair the program has emitted so far. [Days 7](day07_disassembly.md)
and [9](day09_disassembly.md) could hand their VMs a short, precomputable
input list (a phase setting; a diagnostic mode ID) — there is no equivalent
list here. Extending the disassembler for this day meant adding a fourth
dynamic-trace mode, `trace-robot`, that embeds the exact block/resume VM
protocol [`src/day11.rkt`](../../src/day11.rkt)'s `vm-step!` uses and drives
it with the real hull-painting loop, instrumented to also tally an opcode
histogram and relative-mode read/write counts. The trace *is* a run of the
puzzle solution — this is the first day where disassembling the program and
solving the puzzle are the same computation.

## Pass 1 — static recursive descent

```
racket scripts/intcode_disasm.rkt inputs/day11.txt
```

Recursive descent decodes **199 instructions** before running out of
statically-resolvable control flow — but unlike [Day 5](day05_disassembly.md)
(which died after two instructions), descent here covers a lot of ground: it
follows every `if … jump #k` whose target is **immediate mode** (rendered
`#k`), and it turns out both major regions of this program are entered that
way. What defeats it is a specific, recognizable pattern: `jump rel[0]` (and
one `jump mem[521]`) — targets computed at runtime and stored in a cell,
never known on disk. Both regions are still worth reading in the order
descent recovers them.

## The fork (`0 .. 13`)

| Addr | Instruction | Effect |
|-----:|-------------|--------|
| 0 | `mem[8] = INPUT` | Read the **very first** camera reading — the color of panel `(0,0)` before the robot has painted anything. |
| 2 | `if mem[8] != 0 jump #337` | **The fork.** If that first reading is white, jump straight into the relative-base engine at `337` and never come back. Immediate target, so descent follows it. |
| 5 | `if #0 == 0 jump #11` | Unconditional (`0 == 0` is always true) — a goto-via-jump-if-false, falling through to the black-start path. |
| 8, 10 | `0`, `0` | Two data cells, stepped over by the jump — scratch (`mem[9]`, the loop counter below, and `mem[10]`, scratch) sitting inline in the instruction stream rather than after it. |
| 11 | `OUTPUT #1` | Paint the starting panel **white** — unconditionally, regardless of what the camera actually just read. |
| 13 | `OUTPUT #0` | Turn **left** — also unconditional. |

This is worth sitting with: **the fork tests the first camera reading
exactly once.** Nothing after address 13 ever branches back to address 2.
So a Part-1 run that later walks onto a white panel (Part 1 paints 2,129 of
them, definitely including some it later re-visits) never re-triggers the
fork — the relative-base engine at `337` is simply unreachable once the
black-start path is taken, for the rest of the run, no matter what the
camera sees later. The dynamic trace confirms this isn't a guess: Part 1's
entire 102,632-instruction run executes **zero** relative-mode operands and
**zero** `opcode 9`s.

The robot's first decision (paint white, turn left) is also *data-blind* —
it doesn't consult the camera reading it just took at all, it's hardcoded.
The camera value is read only to decide *which fork*, not to inform the
first paint.

## The black-start prologue (`15 .. 336`) — a self-modifying counted loop

This is the code Part 1 actually runs. Structurally it's one loop, executed
**1,058 times**, counted by `mem[9]`:

```
329 | mem[10] = (mem[9] < #1058)
333 | if mem[10] != 0 jump #15
336 | HALT
```

Each iteration reads the camera **10 times** at fixed addresses (`15, 53,
86, 112, 149, 174, 203, 240, 270, 296`), each read followed shortly by a
small derive-and-compare-and-`OUTPUT`-twice block — i.e. each iteration
packs **10 of the puzzle's real decision cycles** (1 input, 2 outputs
apiece) into one straight-line stretch of code, then loops. Two things in
this block are worth naming individually:

**It's self-modifying in the classic Day-5 sense**, not the Day-9 sense.
Several of these mini-blocks write into a nearby cell that is *also* an
operand of an instruction earlier in the same block — e.g. address 71
writes `mem[67] = mem[8]`, and address 67 is the literal-comparison operand
baked into the instruction at address 65 (`mem[10] = (mem[8] == #1)`, whose
`#1` lives at cell 67). On iteration 1 that comparison runs against the
value the program shipped with; from iteration 2 onward it runs against
whatever the *previous* iteration's camera reading left there. Same
mechanism [Day 5](day05_disassembly.md)'s self-test used — an instruction
rewriting a later instruction's operand — just spread across loop
iterations instead of across a single pass.

**Six branches in every iteration are provably dead.** `mem[0]` is never
written anywhere in this program — it permanently holds `3`, the raw value
of the program's *own first opcode cell*, read back as data. Six separate
`if mem[0] == 0 jump …` instructions (addresses `83, 138, 171, 200, 237,
322`) all test that eternally-nonzero cell and can never take their branch.
This is the same "read your own code as a constant" move [Day 9](day09_disassembly.md)'s
`mem[1000] = #3` sentinel made deliberately; here it looks more like a
code-generator artifact (a template that always emits these guard branches
whether or not they're reachable) than a puzzle-specific test. Multiply out
the cost: **6 dead branches × 1,058 iterations = 6,348 branch instructions
that execute and can never fire** — well over half of this region's
control-flow instructions are pure overhead. The dynamic trace's histogram
ties this out exactly: `6,349` jump-if-false executions total = 6,348 dead
ones + the single one-time goto at address 5.

The arithmetic scattered between the real decision blocks (reads of
`mem[1105]`, `mem[1107]`, `mem[1003]`, `mem[1009]`, and similar cells well
past the loaded 659-cell image) is more of the same texture: those
addresses were never written by the loaded program, so under [Day 5](day05_function_guide.md)'s
grow-on-write memory they read as `0` for the entire run, making that
arithmetic provably inert too. None of it was worth hand-decoding
instruction by instruction for this guide — the load-bearing content of
this region is the 10 real input/output pairs per iteration; everything
else is documented, verified-dead padding.

## The relative-base engine (`337 .. 658+`) — real recursion

This is the code Part 2 runs instead, entered directly from the fork and
never visited on the black-start path.

```
337 | REL_BASE += #659
```

`659` is exactly the loaded program's length (`Program: 659 cells`) — the
very first thing this engine does is move the relative base to point one
past the last loaded cell, turning the grow-on-write tail of memory into a
private heap. Identical architectural move to [Day 9](day09_disassembly.md)'s
BOOST program setting `rb` to roam a scratch region past its own image; the
difference is what this engine does with that heap once it has it.

Two `jump rel[0]` sites (`481`, `560`, and a third at `656`) and one `jump
mem[521]` (`643`) are genuine **computed returns**: something earlier writes
a return address into a relative-addressed cell, and control later jumps
through it — a real call/return calling convention, the same idea as Day
9's frame-pointer trick but with the crucial difference that Day 9's targets
happened to *also* be reachable via other static edges (its own guide notes
descent got "essentially the whole program" this way), while several of
Day 11's are not. That's the concrete reason static descent tops out at 199
instructions here instead of covering everything the way it did for Day 9:
not more self-modification, but call targets that genuinely only exist at
runtime, on a cell descent has no way to peek into ahead of time.

The recursive shape is visible even from the static listing alone: `REL_BASE
+= #2` / matching `REL_BASE += #-2` pairs bracket short spans (`458..479`,
`522..558`, `563..654`) the way a function prologue/epilogue would bracket a
call in a stack-based calling convention, each span ending in either a
static jump to the next span or one of the dynamic returns above. Reading
this as "a small recursive function, called some number of times with a
counter argument in a relative-offset register" fits every structural cue
available without needing the dynamic trace to confirm it — though the
trace does: **997 opcode-9 executions** and **thousands** of relative-mode
reads/writes on the Part 2 run, against **zero** of either on Part 1.

Part 1's `panels painted` and Part 2's rendered picture are the puzzle's own
answers, produced as a byproduct of tracing rather than computed separately
— a third independent confirmation of `2129` and `PECKRGZL`, alongside
[`src/day11.rkt`](../../src/day11.rkt) and its
[Python companion](../../python/day11.py).

The size asymmetry is the other headline number: **Part 1 runs 12.7× more
instructions than Part 2**, despite Part 2 doing strictly more per
instruction (relative-mode resolution on most operands, real function
calls). The black-start prologue's 1,058-iteration counted loop dominates
total instruction count regardless of what it accomplishes; the white-start
recursive engine reaches a halt far faster because — per the puzzle's own
mechanics — starting on white steers the robot down a much shorter path to
a hull it's willing to stop painting.

## The problem within the problem

Every earlier Intcode day's "problem within the problem" was about
recognizing a hidden *algorithm* inside a scan (Day 16, Day 19, in the 2018
repo's vocabulary) or a hidden *architecture* inside a bytecode blob (Day
9's calling convention). Day 11's is different in kind: it's about the
**disassembler itself** running out of technique. Static descent has a
principled reason to refuse dynamic jump targets — following them would
mean guessing, not disassembling. Dynamic tracing has always been the
fallback for exactly that gap (Days 5, 7, 9 all lean on it) — but every
prior day's dynamic trace could be *prepared for* by picking a short, known
input list before the first instruction ever runs. Day 11 removes that
option: there is no input list, short or otherwise, that exists independent
of the trace itself, because the Nth input **is** a question about the
world the first N−1 outputs already built. The only way to disassemble this
program completely is to give it the exact interactive environment the
puzzle describes — which means building `paint-hull` wasn't just the
solution to the puzzle, it was also the *only* way to finish the
disassembly. Solving and disassembling converged into one computation.
