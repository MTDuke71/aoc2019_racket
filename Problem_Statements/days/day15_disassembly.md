# Day 15 — Disassembling the repair droid's controller

> Every Intcode program so far has hidden its world in its *behaviour*:
> straight-line arithmetic ([Day 2](day02_disassembly.md)), an obfuscated
> self-modifying self-test ([Day 5](day05_disassembly.md)), a dispatch table of
> tiny modules ([Day 7](day07_disassembly.md)), a relative-base test battery
> ([Day 9](day09_disassembly.md)), a two-headed self-modifying blob
> ([Day 11](day11_disassembly.md)), and — the first that read like compiler
> output — [Day 13](day13_disassembly.md)'s 2,640-cell arcade cabinet with a
> real calling convention.
>
> **Day 15 is the smallest and the most completely understood program of the
> year.** 1,045 cells, of which **70 instructions occupying addresses 0–251
> are the entire code**, with no gaps, no overlaps and nothing left over. It
> has no subroutines, no stack, no relative base, and one loop. Everything from
> 252 up is a **39×20 table**, and that table *is the maze* — not a maze the
> program draws, a maze the program was **compiled around**.
>
> Two consequences. **Static recursive descent recovers all of it**: every jump
> target is an immediate, and the single self-modifying store patches an
> *operand* rather than control flow. And **both puzzle answers are readable
> off the disk with the VM never started** — the oxygen system's coordinates
> are a literal pair of compare immediates at addresses 146 and 153, and the
> walls are one table entry per edge. `254` and `268` come out of arithmetic on
> the image; the droid's 66 ms walk only confirms them.
>
> Generated by [python/day15_disasm.py](../../python/day15_disasm.py) — run
> `python python/day15_disasm.py` to reproduce every number below. Its fourth
> pass asserts the static recovery against the dynamic walk, so this file
> cannot quietly go stale.

## What we're disassembling

1,045 integers — a quarter the size of Day 13's, and the first program this
year that is *smaller* than the thing it describes. The maze has 799 open
squares; the program that serves it is 1,045 cells. That ratio is the tell:
there is no generator in here, no algorithm, no procedural carve. The maze was
carved by whatever produced the puzzle input, and then **frozen into a lookup
table**.

The disassembler is new, and in Python
([python/day15_disasm.py](../../python/day15_disasm.py)) — the Racket
[scripts/intcode_disasm.rkt](../../scripts/intcode_disasm.rkt) is frozen along
with the rest of the Racket tree. Four passes: recursive descent, a memory map,
a static solve straight out of the data region, and a cross-check against the
walk.

### A note on the frozen Racket tool

Run for comparison, `racket scripts/intcode_disasm.rkt inputs/day15.txt`
reports **72** instructions and then this:

```
Static descent decoded only 72 instruction(s) before control
flowed into a cell modified at runtime: this program is
SELF-MODIFYING, so static disassembly is incomplete.
```

Both halves of that are worth unpicking, because the conclusion is wrong and
the reasons are instructive.

**The two extra instructions.** Its own listing shows it decoding address 252
as `2 32 78 22` and 256 as `32 ??? raw=32`. Address 252 is reachable only as
the *fall-through* of the instruction at 249, which is `1105 1 0` — "if `#1`
!= 0 goto `#0`", an **unconditional** jump written with an immediate condition.
There is no fall-through. The Python tool evaluates immediate conditions and
follows only the taken edge, which is why it stops at exactly 70 instructions
and 252 cells. That number is checkable rather than asserted: the widths sum
to 252, the last instruction ends at 252, so the coverage of 0–251 is exact
and gapless — `day15_disasm.py` asserts precisely that.

**The self-modification warning.** It is a true observation with an
over-strong conclusion. The store at 206 does patch a cell at runtime, and the
instruction decoded at 210 does span it — but what it patches is address 211,
which is the *first operand* of `1007 0 37 1044`, not an opcode and not a jump
target. The instruction stays the same instruction; only which cell it loads
from changes. Day 11 earned that warning; Day 15 does not. **Operand
self-modification is data addressing, not code generation** — and on an ISA
with no indexed load, it is the *only* way to index an array.

## Pass 1 — the whole program, 70 instructions

Names for addresses 1032–1044 are assigned from what the code does with them.

### The dispatcher

```
    0 | 3 1033           | cmd = INPUT
    2 | 1008 1033 1 1032 | tmp = (cmd == #1)
    6 | 1005 1032 31     | if tmp != 0 goto #31        ; north
    9 | 1008 1033 2 1032 | tmp = (cmd == #2)
   13 | 1005 1032 58     | if tmp != 0 goto #58        ; south
   16 | 1008 1033 3 1032 | tmp = (cmd == #3)
   20 | 1005 1032 81     | if tmp != 0 goto #81        ; west
   23 | 1008 1033 4 1032 | tmp = (cmd == #4)
   27 | 1005 1032 104    | if tmp != 0 goto #104       ; east
   30 | 99               | HALT
```

A linear if-chain, not a jump table — at four cases that is the cheaper
encoding, and it is what a naive compiler emits anyway.

Address 30 is worth pausing on. **"Any other command is invalid" means the
program halts**, and this is the program's *only* halt: the main loop at 249 is
an unconditional jump back to 0. So the droid controller never terminates on
its own, and the one way to kill it is to send it a bad command. That is
exactly why [python/day15.py](../../python/day15.py)'s `_move` raises on
`halted` rather than looping — the check is unreachable in correct operation
and is a tripwire for a future edit that sends a `0` or a `5`.

### The state, and the missing modulo

Five state variables survive between commands:

| addr | name     | meaning                   |
| ---- | -------- | ------------------------- |
| 1034 | `x`    | position, 1..39           |
| 1035 | `y`    | position, 1..39           |
| 1036 | `xpar` | `x & 1`                 |
| 1038 | `ypar` | `y & 1`                 |
| 1037 | `row`  | which cell-row`y` is in |

Three of those five are **redundant** — `xpar`, `ypar` and `row` are all
functions of `x` and `y`. They exist because **Intcode has no division and no
modulo.** The instruction set is add, multiply, input, output, two jumps, less-
than, equals, adjust-relative-base, halt. There is no way to compute `y & 1`.

So the program does what a compiler does when a recomputation is expensive and
the update is cheap: **strength reduction**. Parity is not computed, it is
*maintained* — a bit toggled by every move along that axis:

```
   31 | ... NORTH
   39 | 1001 1035 -1 1040 | ny    = y + #-1
   43 | 1008 1038 0 1043  | nypar = (ypar == #0)        ; toggle: 0<->1
   47 | 102 -1 1043 1032  | tmp   = #-1 * nypar
   51 | 1 1037 1032 1042  | nrow  = row + tmp           ; row - (ypar == 0)
```

`(v == 0)` is `not v`, which on a 0/1 value is a NOT gate built out of `eq`.
And `row` is a counter carried alongside, decremented on north when leaving an
even row and incremented on south when leaving an odd one — the running index
that `(y - 1) // 2` would have given you if the ISA could divide.

The two horizontal blocks are the same idea with the axes swapped, and they
leave `row` alone because `y` does not change:

```
   81 | 1001 1034 -1 1039 | nx    = x + #-1
   85 | 1008 1036 0 1041  | nxpar = (xpar == #0)
   89 | 101 0 1035 1040   | ny    = #0 + y              ; `mov`, spelled as +0
   93 | 1001 1038 0 1043  | nypar = ypar + #0
   97 | 101 0 1037 1042   | nrow  = #0 + row
```

Note `101 0 1035 1040` — "add immediate 0" is this compiler's `mov`, and like
Day 13's it has interchangeable encodings: `1001 x 0 dst`, `101 0 x dst` and
`1002 x 1 dst` (multiply by one) all appear, sometimes for the same operation
in different blocks. That inconsistency is a **generator fingerprint** — a
human would have picked one.

Every block writes its result into a *shadow* set (`nx`, `ny`, `nxpar`,
`nrow`, `nypar` at 1039–1043) rather than into the live state. The move is only
committed at 227 if the target turns out not to be a wall. This is a candidate
state, evaluated before it is adopted — the reason the puzzle can promise that
a rejected move leaves the droid exactly where it was.

### The tile test — where the maze lives

```
  124 | 1006 1039 217     | if nx == 0 goto #217        ; wall
  127 | 1006 1040 217     | if ny == 0 goto #217
  130 | 1008 1039 40 1032 | tmp = (nx == #40)
  134 | 1005 1032 217     | if tmp != 0 goto #217
  137 | 1008 1040 40 1032 | tmp = (ny == #40)
  141 | 1005 1032 217     | if tmp != 0 goto #217
```

The arena is coordinates **1..39 on both axes**, with 0 and 40 as an
impenetrable border. That is the 41×41 bounding box
[python/day15.py](../../python/day15.py) renders, and it is why the droid can
never escape.

```
  144 | 1008 1039 37 1032 | tmp = (nx == #37)
  148 | 1006 1032 165     | if tmp == 0 goto #165
  151 | 1008 1040 39 1032 | tmp = (ny == #39)
  155 | 1006 1032 165     | if tmp == 0 goto #165
  158 | 1102 2 1 1044     | status = #2 * #1            ; OXYGEN
```

**The oxygen system's location is a literal.** `(37, 39)`, sitting in the
immediate fields at addresses 146 and 153. The droid starts at `(21, 21)`
(the initial values of `x` and `y`), so in the start-relative coordinates this
repo uses everywhere, the oxygen is at `(37-21, 39-21)` = **`(16, 18)`** — the
exact cell the walk finds. No search required; it is two integers in the file.

Then the three-way tile decision:

```
  165 | 2 1041 1043 1032  | tmp = nxpar * nypar
  169 | 1006 1032 179     | if tmp == 0 goto #179
  172 | 1101 0 1 1044     | status = #0 + #1            ; OPEN -- a maze cell

  179 | 1 1041 1043 1032  | tmp = nxpar + nypar
  183 | 1006 1032 217     | if tmp == 0 goto #217       ; WALL -- a pillar
```

`nxpar * nypar` is **AND** and `nxpar + nypar` is **OR**, on values already
known to be 0 or 1. With no bitwise opcodes, arithmetic *is* the boolean
algebra. So:

- **both odd** → a maze cell, always open;
- **both even** → a pillar, always wall;
- **exactly one odd** → an **edge** between two cells, and only then is the
  table consulted.

This is the standard **grid-graph maze encoding**: a 20×20 grid of cells at odd
coordinates, the pillars between them at even coordinates, and one bit per
potential wall. 20×20 cells and their edges land exactly on 1..39 × 1..39.

### Indexing an array on a machine with no indexed load

```
  186 | 1 1042 1043 1032  | tmp = nrow + nypar
  190 | 1001 1032 -1 1032 | tmp = tmp - 1               ; = (ny - 1) // 2
  194 | 1002 1032 39 1032 | tmp = tmp * 39              ; row stride
  198 | 1 1032 1039 1032  | tmp = tmp + nx
  202 | 101 -1 1032 1032  | tmp = tmp - 1
  206 | 101 252 1032 211  | mem[211] = 252 + tmp        ; <-- SELF-MODIFY
  210 | 1007 0 37 1044    | status = (mem[0] < #37)     ; <-- patched operand
  214 | 1106 0 224        | if #0 == 0 goto #224        ; open: fall past 217
  217 | 1102 0 1 1044     | status = #0 * #1            ; the wall arm
  221 | 1105 1 224        | goto #224
```

Read those two lines together and they are one instruction: **`status = (table[idx] < 37)`**, where

```
idx = ((ny - 1) // 2) * 39 + nx - 1        and       table base = 252
```

The `37` is this file's; the threshold is generated per user and the code below
reads it back out of address 212 rather than assuming it. See
[the threshold is per-user](#the-threshold-is-per-user-and-so-is-the-instruction-encoding).

`nrow + nypar - 1` is the program's division-free spelling of `(ny - 1) // 2`,
which is the point of carrying `row` around at all.

The store at 206 writes into address 211 — the first operand slot of the
comparison at 210. The `0` sitting there in the file is a placeholder that is
overwritten before it is ever read. This is the **only** self-modification in
the program, it targets an operand, and it is how you write `a[i]` on an ISA
whose only addressing modes are absolute, immediate and relative-to-a-single-
base register. ([Day 13](day13_disassembly.md) has the same idiom in three
cells, all of them operands, which is why its descent was complete too;
[Day 11](day11_disassembly.md)'s was the genuinely nasty kind.)

That it is the *only* one is checkable, not assumed: of the 70 instructions,
exactly one has a store destination below 252, and that destination is 211.

### `#217` — the single place a wall is written

Every rejection in the program funnels into one three-cell arm:

```
  214 | 1106 0 224        | if #0 == 0 goto #224
  217 | 1102 0 1 1044     | status = #0 * #1
  221 | 1105 1 224        | goto #224
```

`1102 0 1 1044` multiplies immediate `0` by immediate `1` and stores the result
in `status`. It is not arithmetic — it is **`status = 0`**. This ISA has no
"store immediate" instruction, so multiply-by-one and add-zero are its missing
`mov`, and the same idiom is everywhere once you look for it: `status = #2 * #1`
at 158 (oxygen), `status = #0 + #1` at 172 (open cell), and the whole commit
block at 227–243 (`x = nx * #1`, `y = ny + #0`, …).

**Five sites jump here**, and they are exactly the cases that never reach the
table:

| from | test                   | why it is a wall      |
| ---- | ---------------------- | --------------------- |
| 124  | `nx == 0`            | off the west border   |
| 127  | `ny == 0`            | off the north border  |
| 134  | `nx == 40`           | off the east border   |
| 141  | `ny == 40`           | off the south border  |
| 183  | `nxpar + nypar == 0` | both even — a pillar |

The success path does *not* pass through 217, and 214 is why. `1106 0 224` is
"if immediate `0` == 0, goto 224" — an unconditional jump wearing a conditional
opcode, the assembler's `jmp`. The load at 210 has already written
`status = (table[idx] < 37)`, so an open edge arrives at 224 with `status = 1`
intact and 217 is skipped. The five early-outs above branch *into* 217 precisely
because they short-circuit the load that would otherwise have set `status` — the
variable is never cleared at the top of the tile test, so each early-out has to
clear it itself, and they all share the one arm rather than each carrying a copy.

That makes 217 the only cell in the program that writes a `0` into `status`
(1044); the other three writers are 158, 172 and 210. This is the machine-level
reason the droid's reply is an undifferentiated `0` for every kind of
rejection — out of bounds, pillar, or a table entry ≥ 37 all arrive at the
`OUTPUT` at 247 through the same store. The solver in
[python/day15.py](../../python/day15.py) therefore cannot distinguish "border"
from "interior wall", and does not need to.

### Commit, reply, repeat

```
  224 | 1006 1044 247     | if status == 0 goto #247    ; wall: don't move
  227 | ...               | x, y, xpar, ypar, row  <-  nx, ny, nxpar, nypar, nrow
  247 | 4 1044            | OUTPUT status
  249 | 1105 1 0          | if #1 != 0 goto #0          ; forever
```

The commit is skipped on a wall, which is the machine-level statement of "its
position has not changed" — the clause the solution's exact command-count
identity (`2 * (open - 1) + walls`) is built on. See the
[function guide](day15_function_guide.md#the-wall-probe-is-free).

## Pass 2 — memory map

```
  0-251       code        70 instructions: dispatch, four move blocks, tile test
  252-1031    wall table  39 x 20 = 780 entries; entry < 37 means passage
  1032-1044   variables   tmp, cmd, x, y, xpar, row, ypar,
                          nx, ny, nxpar, nrow, nypar, status

  initial state: x=21, y=21, xpar=1, row=10, ypar=1
```

Thirteen variables, three of them redundant-by-necessity, no stack, no heap,
no relative base — the `arb` opcode that [Day 9](day09_disassembly.md)
introduced and Day 13 leaned on for its calling convention is **never used
here**. This program predates nothing and calls nothing; it is a single
`while (true)` around a switch.

The start at `(21, 21)` is cell (11, 11) of the 20×20 grid — near the middle.
The oxygen at `(37, 39)` is cell (19, 20) — the far bottom-right corner.

## Pass 3 — the maze, straight off the disk

Everything above turns into thirteen lines that never start the VM:

```python
def is_open(mem, x, y):
    if not (1 <= x <= 39 and 1 <= y <= 39):
        return False                       # arena border          (addr 124)
    odd_x, odd_y = x & 1, y & 1
    if odd_x and odd_y:
        return True                        # a maze cell           (addr 165)
    if not odd_x and not odd_y:
        return False                       # a pillar              (addr 179)
    return mem[252 + ((y - 1) // 2) * 39 + x - 1] < T    # an edge  (addr 186)
```

`T` is `mem[212]`, the immediate of the compare at 210 — 37 in this file, 35 in
the other one on disk.

Sweep that over the 41×41 arena, mark `(37, 39)` as the oxygen, translate by
the start, and you have the map — identical, cell for cell, to the one the
droid takes 2,456 movement commands and 83,123 VM instructions to build.

```
  maze cells (odd x, odd y)          400
  table entries < 37 (open edges)    399
  open squares = cells + open edges  799
  |E| = |V| - 1 ?                    True  <- a SPANNING TREE

  STATIC part 1 = 254
  STATIC part 2 = 268
```

**This is where the [function guide](day15_function_guide.md)'s tree result
comes from.** Walking the maze establishes empirically that it has no cycles;
the disassembly explains *why*: the table encodes 399 open edges over 400
cells, and 399 = 400 − 1 on a connected graph is a spanning tree by
definition. The puzzle generator carved a **perfect maze** — almost certainly
a randomised-DFS or Kruskal carve — and shipped the result as a lookup table.
The acyclicity was never a property of the algorithm; it was a property of the
file, and now it is one you can point at.

### The threshold is a hole in the value set

The table's 780 entries look like noise: values from 1 to 99, 98 distinct
values, no visible structure. The obfuscation is that **a one-bit fact is
stored as a random seven-bit number** and recovered by a comparison.

Count the values actually present and the trick falls out:

|               |                                                                  |
| ------------- | ---------------------------------------------------------------- |
| values 1..36  | 399 entries —**passage**                                  |
| value 37      | **absent — the only integer in 1..99 that never appears** |
| values 38..99 | 381 entries —**wall**                                     |

The threshold immediate at address 212 is not an arbitrary constant that
happens to separate two clusters; it is a **deliberately vacated value**,
which is why `< 37` and `< 38` produce the identical partition and nothing
else does. Whoever generated this picked a random number below the hole for
"open" and above it for "wall".

Twenty of the 780 entries are never consulted — the last table row covers
`y = 39` and `y = 40`, and `y = 40` is outside the arena. All twenty hold
wall-range values, so even the dead entries are consistent. All 399
passage-valued entries are live, which is why open squares come to exactly
400 + 399.

### The threshold is per-user, and so is the instruction encoding

None of the above is a fact about the puzzle. It is a fact about *this file*,
and the way to find out which is to read someone else's.

`inputs/day15_alt.txt` is a second user's program. Same 1045 cells, same
layout, same 70 instructions — and a different magic number:

| | `day15.txt` | `day15_alt.txt` |
| --- | --- | --- |
| threshold at address 212 | **37** | **35** |
| the vacated value in 1..99 | 37 | 35 |
| passages / walls | 399 / 381 | 399 / 381 |
| spanning tree over 400 cells | yes | yes |
| oxygen literal (146, 153) | (37, 39) | (1, 9) |
| start `x`, `y` (1034, 1035) | (21, 21) | (21, 21) |

So the generator's *structure* is fixed — 20×20 cells, a uniform spanning tree,
399 passages, the same starting square — while the threshold, the hole it sits
in, the oxygen, and the table contents are all drawn per user. A disassembler
that hardcodes `37` produces a confidently wrong maze on the second file rather
than an error, which is the worst failure mode available. Hence
[`wall_threshold`](../../python/day15_disasm.py), which reads T back out of the
compare at 210 and refuses a program that does not have that instruction there:

```python
opcode, destination = mem[210], mem[213]
if (opcode, destination) != (1007, 1044):
    raise ValueError(...)
return mem[212]
```

Pinned by `test_wall_threshold_is_read_out_of_the_compare` and
`test_wall_threshold_is_a_hole_in_the_value_set`, both parameterised over the
two programs, and by `test_wall_threshold_refuses_a_program_it_does_not_recognise`.

**There is a second obfuscation layer, over the code rather than the data.**
Diff the two code regions and forty of the 252 cells differ — but only *three*
of them mean anything: 146 and 153 (the oxygen) and 212 (the threshold). The
other thirty-seven are the generator picking a different spelling of the same
instruction:

```
    35 | 1002 1036 1 1041  ->  102 1 1036 1041     ; xpar*1   vs  1*xpar
    58 | 1001 1034 0 1039  ->  1002 1034 1 1039    ; x+0      vs  x*1
    55 | 1105 1 124        ->  1106 0 124          ; jmp, two ways
   172 | 1101 0 1 1044     ->  1102 1 1 1044       ; status=1: 0+1  vs  1*1
   217 | 1102 0 1 1044     ->  1101 0 0 1044       ; status=0: 0*1  vs  0+0
```

That last line is [the wall arm](#217--the-single-place-a-wall-is-written) in
both files. Because this ISA has no `mov`, a copy has to be written as one of
`x*1`, `1*x`, `x+0`, `0+x`, and a constant as `0*1`, `0+0`, `1*1`, `1*2`, `2*1`
— four or five interchangeable encodings per instruction, all the same width.
Randomising the choice costs the generator nothing and makes a textual diff
between two users' inputs useless.

`test_only_three_code_cells_carry_meaning` proves it by splicing rather than by
reading: take `day15.txt`'s entire code region, move only cells 146/153/212
across from `day15_alt.txt`, bolt on `day15_alt.txt`'s wall table, and the
machine walks the second user's maze exactly — same 799 open squares, same
oxygen — with thirty-seven code cells still textually different.

The disassembler takes a path now, so either file can be read:

```
python python/day15_disasm.py inputs/day15_alt.txt
```

Its pass 4 cross-checks the static recovery against the droid's walk on
whatever file it is given; the locked `(254, 268)` comparison applies only to
`day15.txt`, since the other program's answers belong to someone else's account
and have never been submitted from here.

## What the disassembly is worth

**Day 13 and Day 15 are the two days whose answers are readable without
execution, and they are readable for opposite reasons.** Day 13's world was a
data structure the program was about to *draw*; Day 15's world is a data
structure the program was *compiled around*. In both cases the puzzle's framing
— "run this and watch" — is a narrative device rather than a computational
necessity.

That is worth knowing and worth *not* relying on. The static solve is
input-specific in a way the walk is not: it depends on the maze being a table
rather than a procedure, on the table's stride, on the threshold, and on the
oxygen being a compare immediate. Any of those could have been otherwise, and
on a different user's input at least the constants will be. The 66 ms walk
works on every Day 15 input ever generated. **Read the program to understand
it; run the program to solve it.**

Three techniques from this file that outlive the puzzle:

1. **Strength reduction as a diagnostic.** Redundant state that could be
   recomputed is a fingerprint of a missing instruction. `xpar`, `ypar` and
   `row` exist purely because the ISA cannot divide, and spotting that is what
   turned an opaque five-variable state into "position, plus its parities".
2. **Arithmetic as boolean algebra.** `a * b` is AND, `a + b` is OR and
   `(a == 0)` is NOT once the values are known to be 0/1. Any ISA without
   bitwise ops will do this, and recognising it collapses the tile test from
   six instructions to one line of prose.
3. **Operand self-modification is array indexing.** A store whose destination
   lands inside a later instruction's operand slot is `a[i]`, not
   metaprogramming — and distinguishing it from control-flow self-modification
   is the difference between "static disassembly is complete" and "you will
   need a dynamic trace".
