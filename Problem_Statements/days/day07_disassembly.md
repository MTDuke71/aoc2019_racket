# Day 7 — Disassembling the Amplifier Controller program

> The [function guide](day07_function_guide.md) chains five Intcode copies
> into an amplifier circuit and brute-forces phase permutations. This file
> takes the *single* puzzle program apart — the one every amplifier runs —
> and shows what it actually is: a **phase-indexed jump table** routing to
> ten specialized modules. Part 1's modules (phases 0–4) are compact affine
> calculators; Part 2's (phases 5–9) are **multi-I/O loops** built for the
> feedback wiring.
>
> Generated by [scripts/intcode_disasm.rkt](../../scripts/intcode_disasm.rkt) —
> run `racket scripts/intcode_disasm.rkt inputs/day07.txt` to reproduce.

---

## What we're disassembling

The puzzle input is **523 integers** — one Intcode program copied independently
into each of five amplifiers. Unlike [Day 5](day05_disassembly.md), this
program is **not self-modifying** in the Day 5 sense (no cell is rewritten
and then executed as a new opcode). Instead it uses a subtler trick: the
dispatch jump's target operand **lives at the same address** the prologue
just wrote (`mem[8]`), so static decode of the on-disk bytes misreports the
branch target.

Each amplifier run consumes:

1. **First `opcode 3`:** the phase setting (0–4 in Part 1, 5–9 in Part 2).
2. **Later `opcode 3`s:** input signals from the left neighbour (or `0` on
   the first amp).
3. **`opcode 4`:** one or many outputs, depending on the phase module.

---

## Pass 1 — Static recursive descent (and why it stops early)

Following control flow from address 0, the static decoder sees:

```
addr | raw                      | operation
-----+--------------------------+-------------------------------------
   0 | 3 8                      | mem[8] = INPUT
   2 | 1001 8 10 8              | mem[8] = mem[8] + #10
   6 | 105 1 0                  | if #1 != 0 jump mem[0]
   9 | …                        | data: 21, 38, 55, … (514 data cells)
```

Three instructions, then "data." The jump's position-mode operand is stored
at **address 8**; on disk that cell holds `0`, so static decode prints
`jump mem[0]`. At runtime, instruction 2 has already set `mem[8] = phase +
10`, and instruction 6 reads **that live value** as the pointer — jumping to
`mem[phase + 10]`, i.e. the dispatch table.

This is **operand overlap** (the jump consumes the cell the add just
produced), not self-modifying code. It still defeats static recursive
descent, because the branch target is data-dependent on the phase input.

## The dispatch prologue

Every amplifier run begins with the same three-instruction sequence:

| Step | Effect |
|------|--------|
| `mem[8] = INPUT` | Read phase setting into `mem[8]`. |
| `mem[8] += 10` | Index into the jump table: `mem[8]` becomes `phase + 10`. |
| `if #1 != 0 jump mem[8]` | Always taken; target is `mem[phase + 10]`. |

The jump table occupies `mem[10]` through `mem[19]`:

| Phase | Entry address | Module role |
|------:|--------------:|-------------|
| 0 | 21 | Part 1 — affine `(2·s + 2)·5 + 4` |
| 1 | 38 | Part 1 — affine `(s + 5)·2 + 5` |
| 2 | 55 | Part 1 — affine `((s + 4)·5 + 4)·4 + 4` |
| 3 | 80 | Part 1 — affine `(s + 3)·2 + 3` |
| 4 | 97 | Part 1 — affine `((s + 5)·2 + 3)·5` |
| 5 | 118 | Part 2 — multi-I/O feedback loop |
| 6 | 199 | Part 2 — multi-I/O feedback loop |
| 7 | 280 | Part 2 — multi-I/O feedback loop |
| 8 | 361 | Part 2 — multi-I/O feedback loop |
| 9 | 442 | Part 2 — multi-I/O feedback loop |

(`mem[20] = 99999` is unused padding in the table.)

### Cell-by-cell: `mem[0..22]`

The first 23 integers are the whole **dispatch header**: three instructions,
one padding cell, eleven jump-table slots, and the first two words of the
phase-0 module. Below, *addr* is the memory index; *on disk* is the value
in the puzzle input before any run.

#### Instruction 1 @ `0` — read phase (`3 8`)

| Addr | On disk | Role |
|-----:|--------:|------|
| 0 | `3` | **Opcode** — input (read one value from the amp's input queue) |
| 1 | `8` | **Write target** — store it in `mem[8]` (the phase setting, 0–4 or 5–9) |

After this step: `mem[8] = phase`.

#### Instruction 2 @ `2` — table index (`1001 8 10 8`)

Decoded: `mem[8] = mem[8] + #10` (add; first operand position, second immediate).

| Addr | On disk | Role |
|-----:|--------:|------|
| 2 | `1001` | **Packed instruction** — opcode `01` (add), mode digits `10` |
| 3 | `8` | **Addend A (address)** — read `mem[8]` (the phase just stored) |
| 4 | `10` | **Addend B (literal)** — constant `10` |
| 5 | `8` | **Destination address** — write result back into `mem[8]` |

After this step: `mem[8] = phase + 10` (index into the jump table at `mem[10]`).

#### Instruction 3 @ `6` — dispatch jump (`105 1 0`)

Static decode prints `if #1 != 0 jump mem[0]` — **wrong at runtime** (see
[Pass 1](#pass-1--static-recursive-descent-and-why-it-stops-early) above).

| Addr | On disk | Role |
|-----:|--------:|------|
| 6 | `105` | **Packed instruction** — opcode `05` (jump-if-true), mode digit `1` |
| 7 | `1` | **Condition (literal)** — `#1`, always non-zero → branch always taken |
| 8 | `0` | **Jump-target pointer** — position mode: jump to address `mem[8]`. **Operand overlap:** this cell *is* `mem[8]`; instruction 2 just wrote `phase+10` here, so the jump goes to address **`mem[phase + 10]`** (a table entry), not `mem[0]`. |

After this step: `ip` = module entry for this phase (e.g. phase `0` → `21`).

#### Padding @ `9`

| Addr | On disk | Role |
|-----:|--------:|------|
| 9 | `0` | **Unused.** Fall-through slot after the jump (`6+3=9`), but control never arrives here. |

#### Jump table @ `mem[10..20]`

Data cells, not opcodes. The jump effectively does `ip ← mem[mem[8]]` where
`mem[8] = phase + 10`:

| Addr | On disk | When `mem[8]` equals this addr | Points to |
|-----:|--------:|--------------------------------|-----------|
| 10 | `21` | phase **0** | Part 1 module @ 21 |
| 11 | `38` | phase **1** | Part 1 module @ 38 |
| 12 | `55` | phase **2** | Part 1 module @ 55 |
| 13 | `80` | phase **3** | Part 1 module @ 80 |
| 14 | `97` | phase **4** | Part 1 module @ 97 |
| 15 | `118` | phase **5** | Part 2 module @ 118 |
| 16 | `199` | phase **6** | Part 2 module @ 199 |
| 17 | `280` | phase **7** | Part 2 module @ 280 |
| 18 | `361` | phase **8** | Part 2 module @ 361 |
| 19 | `442` | phase **9** | Part 2 module @ 442 |
| 20 | `99999` | phase 10 (impossible here) | Sentinel / padding — not valid code |

One-line summary: **`mem[10 + phase]`** is the start address of that phase's
micro-program.

#### Head of phase-0 module @ `21..22`

When phase is `0`, control lands here — no longer dispatch, but the amplifier
body (see [Part 1 modules](#part-1-modules-phases-04--static-disassembly)).

| Addr | On disk | Role |
|-----:|--------:|------|
| 21 | `3` | **Opcode** — second input (the **signal** from the left neighbour, or `0` on amp A) |
| 22 | `9` | **Write target** — store signal in `mem[9]` (the module's working register) |

Cells `23+` continue the phase-0 affine map (`mem[9] = 2 + mem[9]; …; OUTPUT;
HALT` → output `5s + 14`).

#### End-to-end using only these 23 cells

```
INPUT → mem[8]              (cells 0–1)
mem[8] += 10                (cells 2–5; result written back to cell 8)
jump mem[8]                 (cells 6–8; cell 8 holds phase+10)
  → ip = mem[10 + phase]    (one of cells 10–19)
  → phase 0: ip = 21        (cells 21–22: read signal into mem[9])
```

Nine cells are executable prologue (with **`mem[8]` triple duty** as phase
storage, add destination, and jump-operand slot), one is padding, eleven are
the dispatch table, two are the start of the selected module.

The canonical name for this shape is a **jump table** / **computed goto**
dispatch on the phase setting — the same pattern as a `switch(phase)` with
ten case labels, except the labels are addresses baked into data.

## Part 1 modules (phases 0–4) — static disassembly

Each Part 1 module is a straight-line basic block: read signal `s` into
`mem[9]`, apply a fixed affine formula, emit once, halt. Example — phase 0
(entry 21):

```
  21 | mem[9] = INPUT          ; signal s
  23 | mem[9] = #2 + mem[9]    ; s + 2
  27 | mem[9] = mem[9] * #5    ; 5(s + 2)
  31 | mem[9] = mem[9] + #4    ; 5(s + 2) + 4  =  5s + 14
  35 | OUTPUT mem[9]
  37 | HALT
```

Dynamic trace with inputs `[phase, signal=0]` confirms each module:

| Phase | Instructions | Output (s = 0) | Affine form |
|------:|-------------:|---------------:|-------------|
| 0 | 8 | 14 | `5s + 14` |
| 1 | 8 | 15 | `2s + 15` |
| 2 | 10 | 100 | `20s + 100` |
| 3 | 8 | 9 | `2s + 9` |
| 4 | 9 | 65 | `10s + 65` |

Opcode histogram per phase: only `add`, `mul`, `in`, `out`, and the prologue
`jump-if-true` — **no comparisons, no Part 2-style control flow**. Part 1's
puzzle work is entirely in the **permutation search** over how the five
affine maps compose in series, not in deciphering the Intcode.

## Part 2 modules (phases 5–9) — static disassembly

Part 2 reuses the same prologue but routes phases 5–9 to **longer modules**
at entries 118, 199, 280, 361, and 442. Each is a repeating pattern:

```
  INPUT  →  transform mem[9]  →  OUTPUT  →  INPUT  →  …  →  HALT
```

Example opening of phase 5 (entry 118):

```
 118 | mem[9] = INPUT
 120 | mem[9] = mem[9] * #2
 124 | OUTPUT mem[9]
 126 | mem[9] = INPUT
 128 | mem[9] = #1 + mem[9]
 132 | OUTPUT mem[9]
  …
```

A single `[phase, signal]` trace **blocks on the third INPUT** — these
modules expect a **stream** of signals from the feedback loop, not one shot.
That is exactly why [Day 7 Part 2](day07_function_guide.md) needs
`vm-step!` to yield `'blocked` instead of erroring: the program is written
for cooperative multi-amp scheduling.

Static disassembly of the full Part 2 modules is faithful (no runtime opcode
synthesis); dynamic traces require running the five-VM feedback scheduler,
not a single-input `trace-exec`.

## The problem within the problem

Seen through the disassembly lens, Day 7 splits cleanly:

| Layer | What the puzzle asks | What the program is |
|-------|---------------------|---------------------|
| **Outer** | Best phase permutation over five amps | Search problem (120 orderings) |
| **Middle** | Series chain (P1) vs feedback loop (P2) | Wiring / scheduling model |
| **Inner** | Run Intcode correctly | Phase dispatch + ten tiny subprograms |

The Intcode is not hiding a obscure algorithm — it is a **test harness** that
(1) reads the phase once, (2) jumps to the matching micro-program, and (3)
either computes one affine output (Part 1) or cycles on I/O (Part 2). The
puzzle difficulty is combinatorial (which permutation maximizes the final
thruster signal), not reverse-engineering 523 integers of obfuscated logic.

Contrast [Day 5](day05_disassembly.md): there the input *was* the obfuscation
(self-modifying opcode dispatch on system ID). Here the dispatch is a plain
jump table; the "meta-problem" is the **amplifier topology** imposed by Part 2.

## Disassembly-theory connections

- **Jump table dispatch** — the prologue is isomorphic to
  `targets[phase]()` where `targets[]` is `{21, 38, …, 442}`. Static
  disassemblers that don't execute the prologue see only three instructions
  and a sea of data.
- **Operand overlap** — the jump at ip 6 reads address 8, which instruction 2
  just updated. Real binaries do similar things (e.g. PC-relative fixups,
  table-driven interpreters). It is weaker than Day 5's "write the next
  opcode," but equally invisible to on-disk CFG analysis.
- **Dynamic trace with input queue** — faithful for Part 1 modules (two
  inputs suffice). Part 2 needs **multi-input trace** or full-system
  simulation — the extension [day05_disassembly.md](day05_disassembly.md)
  foreshadowed for Day 7.

**Rust analogue:** ten `fn amplify_phaseN(signal: i64) -> i64` functions and
a `match phase { 0..=9 => TARGETS[phase](signal) }` dispatcher — the
Intcode is a bytecode encoding of exactly that.
