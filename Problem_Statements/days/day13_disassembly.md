# Day 13 — Disassembling the arcade cabinet

> Every Intcode program so far has been hand-rolled: straight-line arithmetic
> ([Day 2](day02_disassembly.md)), an obfuscated self-modifying self-test
> ([Day 5](day05_disassembly.md)), a dispatch table of tiny modules
> ([Day 7](day07_disassembly.md)), a relative-base test battery
> ([Day 9](day09_disassembly.md)), a two-headed self-modifying blob
> ([Day 11](day11_disassembly.md)). **Day 13's 2,640 cells are the first that
> read like compiler output.** There is a calling convention — caller writes
> the return address into `rel[0]` and arguments into `rel[1..k]`, callee
> shifts the relative base by the frame size so arguments become `rel[-k..-1]`,
> return value goes back into the first argument slot, `jump rel[0]` is `ret`.
> There is a heap: two 1,000-cell arrays past the code. There is an idiom set
> for the instructions the ISA lacks (`li`, `mov`, `jmp`, indexed load/store),
> each with two interchangeable encodings — the fingerprint of a generator.
>
> Two consequences, both the opposite of Day 11. **Static recursive descent
> recovers the entire program** (196 instructions, no gaps): every call site is
> an immediate-mode jump, and the three self-modified cells patch *operands*,
> never control flow. And **both puzzle answers are readable off the disk
> without running the machine**: the starting screen is a literal 40×25 tile
> array, and the score is an order-independent sum over a point-value table
> hidden behind an affine permutation. `348` and `16999` fall out of arithmetic
> on the image; the three instrumented dynamic runs below only confirm them.
>

## What we're disassembling

2,640 integers — the largest program of the year so far, and the first the VM
is *imported* for rather than re-derived ([`src/intcode.rkt`](../../src/intcode.rkt),
see the [function guide](day13_function_guide.md)). The disassembler gains a
`day13` mode with four passes: static recursive descent, a recovered memory
map, a **static** solve of both parts straight from the data regions, and
three instrumented dynamic runs (no poke / free play / a deliberate loss).

The static solve is the interesting addition. Day 11 pushed the disassembler
into *needing* a dynamic trace, because the Nth input was a question about a
world the first N−1 outputs had built. Day 13 pushes it the other way: the
cabinet's whole world is a data structure sitting in the file, so the
disassembler can answer the puzzle by reading rather than executing.

## Pass 1 — static recursive descent, and it wins

```
racket scripts/intcode_disasm.rkt inputs/day13.txt
```

**196 instructions, the whole program.** Descent follows `if #1 != 0 jump #578`
(this compiler's `call`) because the target is immediate; it stops only at the
`jump rel[0]` returns, which by then are all inside routines it has already
walked into from their call sites. Compare [Day 11](day11_disassembly.md),
where descent topped out at 199 of 659 cells because call *targets* were
computed at runtime. Here only the returns are dynamic, and returns are the
one dynamic edge you can afford to lose.

Two things in the listing look like disassembler bugs and are actually
findings:

**The patched-operand instructions render with their on-disk operand.** Three
cells (435, 566, 593) are overwritten at runtime with a computed address, so
descent shows `mem[386] = mem[386] + mem[0]` where the machine will really
execute `mem[386] = mem[386] + mem[1639 + slot]`. That's not descent being
wrong — it's descent faithfully reporting that the instruction is incomplete
until the program finishes writing it.

**The run of `mem[1] = mem[1] + mem[1]` at 639 is not code.** Address 636 is
`if #0 == 0 jump rel[0]` — an unconditional `ret` whose fall-through can never
execute. Descent queues the fall-through anyway and lands in the board array,
where a row of 40 wall tiles (`1, 1, 1, 1, …`) decodes as forty-cells-worth of
plausible-looking adds. The garbage *is* the top wall of the screen, and it is
how the array base 639 announces itself in the listing.

## The head (`0 .. 11`) — a tamper guard that is really a parser self-test

| Addr | Instruction | Effect |
|-----:|-------------|--------|
| 0 | `mem[385] = mem[380] + mem[379]` | The free-play flag. `mem[380] = 1`, `mem[379] = 0`, so this computes **1**. |
| 4 | `mem[381] = (mem[2639] == #310356)` | Checksum: is the **last cell of the image** still the magic constant? |
| 8 | `if mem[381] != 0 jump #12` | Pass → run. |
| 11 | `HALT` | Fail → stop, silently, with zero output. |

The first thing the year's biggest program does is check that you loaded it
correctly. A parser that drops a trailing token, keeps a newline, or pads by
one produces a cabinet that halts at address 11 having emitted nothing — no
error, no partial screen, just an empty output stream. The fact that
[`src/day13.rkt`](../../src/day13.rkt) gets a picture at all is a passing test
of `parse-input` on 2,640 cells.

The canary also sits exactly one cell past the end of the point-value array
(1639 + 1000 = 2639), which makes it a bounds tripwire as well as a load
check: anything that runs one entry off the end of that table lands on it.

## The quarters patch is an opcode rewrite

The puzzle says "set memory address 0 to 2 to play for free". Address 0 is not
a flag cell — it is the **opcode of the first instruction**:

```
on disk :  1 380 379 385     mem[385] = mem[380] + mem[379]   =  1 + 0  = 1
poked   :  2 380 379 385     mem[385] = mem[380] * mem[379]   =  1 * 0  = 0
```

Poking a `2` turns an `add` into a `mul`, and the two constants parked at 379
and 380 were chosen so that `1 + 0 = 1` and `1 × 0 = 0`. The flag it computes
is tested exactly once, at the bottom of the board-drawing loop:

```
65 | if mem[385] == 0 jump #69     ; free play → fall into the game
68 | HALT                          ; demo mode → the board was the whole show
```

So Part 1 and Part 2 are not "the same program with a flag set" — they are the
same program with a **different instruction at address 0**, and the
`vm-poke!` in [`play`](../../src/day13.rkt) is self-modifying code that the
puzzle asks *you* to write. The [function guide](day13_function_guide.md)
notes that free play arrives on a channel distinct from opcode 3; the
disassembly sharpens that: it arrives on a channel distinct from *data*.

Address 0 is reused as scratch later (the score-add at 433 reads
`mem[cell 435]`, and cell 566 is a patched operand), which is why the guard at
address 4 checks cell 2639 rather than a checksum over the whole image — the
image doesn't stay constant.

## Memory map

```
    0 ..   11 : tamper guard
   12 ..   68 : draw-the-board loop (y in 0..24, x in 0..39)
   69 ..  378 : the game loop (joystick, paddle, ball physics)
  379 ..  392 : registers — the compiler's globals
  393 ..  636 : subroutines
  639 .. 1638 : screen array, 40 x 25, row-major
 1639 .. 2638 : point-value array, indexed by an affine permutation
         2639 : the tamper canary
 2640 .. 2654 : the stack (relative base starts here; max depth 15 cells)
```

`REL_BASE += #2640` at address 12 sets the base to exactly the program's
length — the same "turn grow-on-write memory past my own image into a heap"
move [Day 9](day09_disassembly.md)'s BOOST program and
[Day 11](day11_disassembly.md)'s engine both make. The difference is that
Day 13 uses it as a genuine **call stack** with a fixed maximum depth: the
deepest chain is `break_block` (+3) → `slot` (+3) → `mod` (+8), so the base
never exceeds 2654. Fifteen cells of stack for the entire game.

### Registers (379 .. 392)

| Cell | Initial | Role |
|-----:|--------:|------|
| 379 | 0 | constant `0` — operand of the instruction at address 0 |
| 380 | 1 | constant `1` — the other operand |
| 381 | 0 | scratch: **every** comparison result in the program lands here |
| 382 | 0 | draw-loop cursor x |
| 383 | 0 | draw-loop cursor y |
| 384 | 0 | joystick reading — *and*, later in the same tick, the "did we bounce?" flag |
| 385 | 0 | free-play flag (computed at address 0) |
| 386 | 0 | score |
| 387 | **348** | blocks remaining |
| 388 | 18 | ball x |
| 389 | 20 | ball y |
| 390 | 1 | ball dx |
| 391 | 1 | ball dy |
| 392 | 20 | paddle x |

`mem[387] = 348` is Part 1's answer, shipped as an initialised data cell. The
program counts its own blocks down to zero to know when the game is won, so it
has to carry the count — and carrying it means the answer is a literal.

Cell 384 doing double duty (joystick reading, then bounce flag) is a register
allocator reusing a global whose live ranges don't overlap. It is the clearest
single tell that this program was generated rather than written.

## The calling convention

```
  caller                              callee (entry at T)
  ------                              -------------------
  rel[1] = arg1                       REL_BASE += F        ; F = frame size
  rel[2] = arg2                       ...  args are now rel[-F+1 .. ]
  rel[0] = <return address>           ...  return value → first arg slot
  if #1 != 0 jump #T                  REL_BASE -= F
  <return address>: ...               if #0 == 0 jump rel[0]      ; ret
```

| Entry | Signature | Frame | What it does |
|------:|-----------|------:|--------------|
| 393 | `break_block(x, y)` | 3 | erase the tile, look up its value, add to score, decrement the counter |
| 456 | `mod(n, a, c, m)` | 8 | `(n*a + c) mod m` — the ISA has no division |
| 549 | `draw(x, y, tile)` | 4 | store into the screen array **and emit** `(x, y, tile)` |
| 578 | `tile_at(x, y)` | 3 | load from the screen array |
| 601 | `slot(x, y)` | 3 | address of `(x,y)`'s point value |

`mod`'s frame of 8 is 1 return address + 4 arguments + 3 locals; every other
routine's frame is exactly 1 + its argument count, with no locals. That's a
frame layout computed per-routine, not a fixed convention — another
compiler tell.

### The idiom set

Intcode has no move, no load-immediate, no unconditional jump, and no indexed
addressing. This program synthesises all four, and uses **two interchangeable
encodings for each**, alternating with no discernible pattern:

| Pseudo-instruction | Encoding A | Encoding B |
|---|---|---|
| `li r, k` | `add #0, #k` (`21101 0 37 0`) | `mul #k, #1` (`21102 138 1 0`) |
| `mov r, s` | `add s, #0` (`21001 388 0 1`) | `mul #1, s` (`20102 1 382 1`) |
| `jmp t` | `jt #1, t` (`1105 1 578`) | `jf #0, t` (`1106 0 549`) |
| indexed | patch the operand cell | (no alternative) |

Nothing chooses between A and B — both are the same length and the same cost.
A human writing 2,640 cells by hand converges on one habit; a generator
emitting from a template table with randomised equivalents produces exactly
this. (AoC's inputs are per-user, so the generator is real.)

## Indexed addressing by operand patching

Position mode dereferences once: `mem[k]`, with `k` a literal in the
instruction. There is no `mem[mem[k]]`. So an array subscript has to be built
by *writing the address into the instruction that will read it* — the
[Day 5](day05_disassembly.md) self-modification trick, used here not as
obfuscation but as the only available addressing mode.

The store, `draw(x, y, tile)` at 549:

```
549 | REL_BASE += #4
551 | mem[566] = rel[-2] * #40        ; y * stride
555 | mem[566] = rel[-3] + mem[566]   ;   + x
559 | mem[566] = #639 + mem[566]      ;   + base        → cell 566 now holds the address
563 | mem[???] = rel[-1] + #0         ; cell 566 IS this instruction's destination operand
567 | OUTPUT rel[-3]                  ; x
569 | OUTPUT rel[-2]                  ; y
571 | OUTPUT rel[-1]                  ; tile
573 | REL_BASE += #-4
575 | if #1 != 0 jump rel[0]          ; ret
```

The load, `tile_at(x, y)` at 578, is the mirror image: same three lines of
address arithmetic into cell 593, which is the *source* operand of the
instruction at 592, whose result goes into `rel[-2]` — the first argument slot,
i.e. the return value.

Two observations worth keeping:

**The display is memory-mapped.** The three `OUTPUT`s live *inside* the store
routine. Every write to the screen array is mirrored to the output port, by
construction — a write-through cache, not a render pass. That is why the
puzzle's output stream is a stream of *draw commands* and not a frame dump,
and why erasing a tile (`draw(x, y, 0)`) shows up on the wire exactly like
drawing one.

**The initial paint uses a different path.** The board-drawing loop at 12..68
calls `tile_at` and then does its own three `OUTPUT`s inline (37..41) rather
than calling `draw`. It reads the array without writing it, so the
write-through path would never fire. Two display paths, one for the full
repaint and one for in-game diffs.

## `mod` at 456 — octal restoring division

Intcode has add, multiply, and comparisons. No divide, no remainder. So the
point-value hash needs its modulus built by hand:

```
456 | REL_BASE += #8
458 | rel[-3] = rel[-7] * rel[-6]     ; n * a
462 | rel[-3] = rel[-3] + rel[-5]     ;      + c
466 | rel[-2] = rel[-4] * #64         ; 64m — subtract while it fits
477 |   rel[-3] -= rel[-2]            ;   (loop)
492 | rel[-2] = rel[-4] * #8          ; 8m  — subtract while it fits
503 |   rel[-3] -= rel[-2]            ;   (loop)
518 | rel[-4]                         ; m   — subtract while it fits
525 |   rel[-3] -= rel[-4]            ;   (loop)
540 | rel[-7] = rel[-3]               ; return value into arg slot 1
544 | REL_BASE += #-8
546 | if #0 == 0 jump rel[0]          ; ret
```

Three ladders — 64m, 8m, m — is **restoring division with three base-8
digits**. Each ladder is a `while`, so any one of them alone would be correct;
the other two are there for speed, and the ladder is sized to the constants
this routine will actually see. The largest possible dividend is
`999 × 503 + 366 = 502,863`, so no ladder can iterate more than 7 times
(21 subtractions worst case instead of up to 502), and a fourth ladder at
`512 × 1000 = 512,000` could never fire. Whoever generated this program knew
the range of its own hash.

Cost, measured: **47.3 instructions per call, averaged over the 348 calls in a
full game** — 16,457 instructions, 2.7% of the run. It is called once per block
broken and nowhere else. Had `slot`/`mod` been called per *tile lookup*
instead (16,912 lookups in a full game) it would dominate. The layout keeps it
off the hot path.

## The hidden score map

`slot(x, y)` at 601 computes an address, then `break_block` patches it into
the score-add:

```
slot(x, y) = 1639 + ((25*x + y) * 503 + 366) mod 1000
```

Three layers of indirection on one 1,000-cell array:

1. **Different linearisation.** `25*x + y` is *column-major*; the screen array
   at 639 is *row-major* (`40*y + x`). Same 1,000 cells, transposed index.
2. **Affine scramble.** `gcd(503, 1000) = 1`, so `n ↦ (503n + 366) mod 1000` is
   a bijection on `0..999` — a permutation, not a hash with collisions. Every
   board cell has exactly one point value and vice versa. (The inverse
   multiplier is `503⁻¹ ≡ 167 (mod 1000)`, if you ever want to read the table
   forwards.)
3. **Values for non-blocks too.** All 1,000 entries are populated (1..98,
   summing to 47,892), including the 652 cells that are wall, empty, ball or
   paddle. Only the 348 block cells are ever read, so 65% of the table is
   camouflage.

## The game loop (`69 .. 378`)

One tick, in the order the code runs it:

```
 69 | OUTPUT #-1 / OUTPUT #0 / OUTPUT mem[386]   ; publish the score
 75 | mem[384] = INPUT                           ; joystick
 77 | ... < 0 ? -> 94 ;  > 0 ? -> 108 ;  else -> 161      (no move)
 94 | if !(#1 < mem[392])   jump 161             ; left clamp:  paddle > 1
108 | if !(mem[392] < #38)  jump 161             ; right clamp: paddle < 38
119 | draw(mem[392], 23, 0)                      ; erase the paddle
138 | mem[392] += mem[384]                       ; move it
142 | draw(mem[392], 23, 3)                      ; redraw it
161 | mem[384] = 0                               ; REUSE 384 as the bounce flag
165 | t = tile_at(ball_x + dx, ball_y)           ; probe 1: horizontal
    |   t == 0 -> nothing ; t == 2 -> break_block ; else nothing
205 |   dx = -dx ; flag = 1                      ;   (unless t was 0)
213 | t = tile_at(ball_x, ball_y + dy)           ; probe 2: vertical
253 |   dy = -dy ; flag = 1
261 | if flag jump 161                           ; something bounced -> re-probe
264 | t = tile_at(ball_x + dx, ball_y + dy)      ; probe 3: diagonal
304 |   dx = -dx ; dy = -dy ; flag = 1
316 | if flag jump 161                           ; re-probe
319 | draw(ball_x, ball_y, 0)                    ; erase the ball
338 | ball_x += dx ; ball_y += dy                ; move it
346 | draw(ball_x, ball_y, 4)                    ; redraw it
365 | if ball_y < #24 jump 75                    ; next tick
372 | OUTPUT #-1 / OUTPUT #0 / OUTPUT #0 ; HALT  ; you lost
```

Four things this makes explicit that the puzzle prose does not:

**Collision resolution is a fixed point, not a pass.** Lines 261 and 316 jump
back to 161, which resets the flag and re-runs all three probes. A ball that
bounces keeps re-probing until a full pass finds nothing — which is what
[the trace](#pass-2--dynamic-confirmation-three-ways-to-run-the-cabinet)
measures as 3.33 `tile_at` calls per tick rather than a flat 3.

**A paddle is a wall that moves; a block is a wall that disappears.** Only
tile-id 0 lets the ball through. Tile 2 gets `break_block` called on it *and
then* falls into the same `dx = -dx` as a wall. There is no separate
"paddle hit" case anywhere in the program — the paddle bounces the ball
because it is solid, not because it is special.

**The lose line is one row below the paddle.** The paddle sits at `y = 23`
(the literal in the `draw` calls at 123 and 146); the game ends when the ball
reaches `y = 24`. So a miss is detectable one tick after it becomes
inevitable, and the paddle's own row is still a legal ball position.

**The paddle clamp gives it 1..38, not 0..39.** `mem[392] > 1` guards a left
move and `mem[392] < 38` guards a right move, so the paddle can never be drawn
on top of the wall columns at `x = 0` and `x = 39`. A controller that asks for
a move at the edge doesn't error — the clamp silently jumps to 161, and the
paddle stays put. It never fires in the tracking run: 4,777 non-zero joystick
reads produce exactly 4,777 paddle redraws, so every requested move was
allowed.

### The fixed point has no bound — the cabinet can livelock

Re-probing after every bounce is elegant right up until it doesn't terminate,
and nothing in the program says it must. The loop assumes that flipping a
velocity component eventually finds a free cell on that axis. It doesn't when
**both** x-neighbours are solid:

```
ball=(1,23) vel=(1,1) paddle_x=2        ip=183, inside the probes

   y=22  .##....
   y=23  .##o=..    probe x: tile(2,23) = 3 (paddle) -> solid -> dx = -1, flag
   y=24  .##....    re-probe: tile(0,23) = 1 (wall)  -> solid -> dx = +1, flag
                    re-probe: the paddle again … forever
```

The ball is wedged in the one-cell gap between the left wall and the paddle,
**on the paddle's own row**. Every pass sets the bounce flag, so 261/316 jump
back to 161 unconditionally and the machine never reaches its next `INPUT`.
Note that the livelock *preempts* the loss: the ball would have crossed to
`y = 24` on the very next move, but there is no next move.

It happens at either wall, and it is not rare: 3 of the 736 swept starting
configurations wedge — `(paddle 6, ball 4, vel (−1,1))` and
`(paddle 8, ball 6, vel (−1,−1))` against the left wall, `(paddle 33, ball 35,
vel (1,1))` against the right one. All three are the same picture mirrored:
ball moving *into* a wall with the paddle just inside it.

This is not reachable from the shipped starting state (4,778 ticks, clean
halt), but it is reachable in ordinary play — hold a direction while the ball
comes down a wall column and the paddle can arrive beside it on exactly the
tick the ball occupies `(1, 23)`. It was found by accident, by sweeping
alternative start positions (below), and it is why
[scripts/day13_arcade.rkt](../../scripts/day13_arcade.rkt) puts a watchdog on
each tick: faithful emulation of this program can hang its host.

A bounded version costs one instruction's worth of thought — cap the re-probe
at two passes, or drop the flag when a pass changes nothing — so this reads as
a generator that never tested the paddle against a wall, not as a deliberate
trap. It is the only defect the disassembly turned up in an otherwise
notably well-built program.

## Both answers, statically

**Part 1** is `count of tile-id 2 in cells 639..1638` = **348**, cross-checked
against the literal at `mem[387]` = 348. The tile histogram of the image is
`empty 562, wall 88, block 348, paddle 1, ball 1` — and the dynamic run
confirms the program's initial 1,000 draw commands reproduce those cells
exactly (`starting screen matches the disk image: #t`).

**Part 2** is `Σ mem[slot(x,y)]` over the 348 block cells = **16999**.

The reason that sum is the answer — and not merely an upper bound — is a
three-line argument the disassembly makes checkable:

* The only write to the score is `mem[386] += mem[<patched>]` inside
  `break_block`, called once per block, from the collision probe that just
  identified tile-id 2.
* `break_block` immediately overwrites that tile with 0, so no block is broken
  twice; and `mem[387]` counts down to 0, at which point the program emits the
  score and halts (450). It halts *because* every block was broken.
* Addition commutes. **The final score does not depend on the order blocks are
  broken in, on how long the game takes, or on how well you play** — only on
  which blocks are broken, and the halt condition says: all of them.

So Part 2 has no path dependence at all. The "game" is a very elaborate
delivery mechanism for a sum you can compute with a `for` loop over the image.

**Tested, not just argued.** Patch the ball and paddle to different starting
positions — in the registers *and* in the screen array, since a stale tile
would act as a solid obstacle — and replay with the same tracking controller:

| ball | velocity | paddle | ticks | score |
|---|---|---:|---:|---:|
| (18,20) | (1,1) | 20 | 4,778 | **16999** |
| (36,20) | (1,1) | 38 | 5,196 | **16999** |
| (24,20) | (1,1) | 30 | 6,276 | **16999** |
| (18,20) | (1,−1) | 20 | 6,446 | **16999** |
| (12,20) | (1,1) | 12 | 7,700 | **16999** |
| (30,20) | (1,1) | 30 | 8,044 | **16999** |
| (28,20) | (−1,−1) | 20 | 8,814 | **16999** |

Seven trajectories differing by 84% in length, one score. Widening that to
every legal paddle column (1..38) against ball starts near it and all four
initial velocities — 736 configurations, **624 of them wins** — the range of
durations grows to 4,025 … 10,531 ticks and the set of scores stays exactly
`{16999}`. Order-independence isn't an argument that happens to hold; it is
the only thing 624 different games agree on.

What *does* vary is whether you get a score at all: 109 of those starts lose in
four ticks and report `0`, because the ball begins three rows above the lose
line and the tracking controller is only safe once it is already under the ball
— the boundary condition the [function guide](day13_function_guide.md)'s parity
argument assumes rather than proves. Three more
([ball (6,20), paddle 12](#the-fixed-point-has-no-bound--the-cabinet-can-livelock)
among them) never terminate at all.

The one thing that *can* change the answer is losing, and the program is blunt
about it:

```
365 | if mem[389] < #24 jump #75      ; ball above the lose line → next tick
372 | OUTPUT #-1 / OUTPUT #0 / OUTPUT #0
378 | HALT
```

A miss emits the score sentinel with value **0** and halts. There is no
partial credit — a driver that drops the ball reports `0`, not "however far it
got". The disassembler runs this deliberately (joystick wired to 0): 16 ticks,
2 blocks broken, score events `0, 14, 87, 0`, final score **0**.

## Pass 2 — dynamic confirmation, three ways to run the cabinet

|---|---:|---:|---:|

Everything in that table closes exactly, which is the real value of running it:

**Part 1's `adjust-rel-base` count decomposes.** `2001 = 1 + 2 × 1000`: one
`REL_BASE += 2640` at address 12, then one enter/exit pair per `tile_at` call,
one call per screen cell. The board loop touches every cell exactly once and
reads input **zero** times — which is why
[`src/day13.rkt`](../../src/day13.rkt)'s `no-joystick` can be an `error` rather
than a value.

**Part 2's draw commands decompose too.** `20,456 = 1,000` initial paint
`+ 348` block erases `+ 4,777 × 2` ball erase/redraw `+ 4,777 × 2` paddle
erase/redraw. Per-tile: `empty 10,464, wall 88, block 348, paddle 4,778,
ball 4,778`. The 4,777s are one short of the 4,778 ticks because the game halts
*inside* `break_block` on the last brick, mid-frame, before the ball is
redrawn.

**The paddle moves on every tick but one.** Joystick histogram over the 4,778
reads: `-1` 2,386 times, `+1` 2,391 times, `0` exactly **once**. The
[function guide](day13_function_guide.md)'s parity argument (`g' = g + Δball ± 1`
never grows `|g|`, so tracking is safe) predicts the paddle stays glued to the
ball; the trace shows it is glued *while never resting* — ball and paddle are
essentially never x-aligned at the instant the joystick is read.

**349 score events = 1 + 348.** One at address 69 (the initial `0`, emitted
before the first joystick read) plus one per brick, with 348 deltas in the
range 1..98 summing to 16,999. That is the static prediction, re-derived one
brick at a time.

**Where the 605,195 instructions go.** Attributing each executed instruction
to the region its `ip` fell in, over the Part 2 run:

| Region | Calls | Instructions | Per call |
|---|---:|---:|---:|
| game loop (69..392) | — | 255,249 | — |
| `draw` (549) | 19,456 | 194,560 | 10.0 |
| `tile_at` (578) | 16,912 | 118,384 | 7.0 |
| `mod` (456) | 348 | 16,457 | 47.3 |
| board repaint (12..68) | — | 10,103 | — |
| `break_block` (393) | 348 | 6,611 | 19.0 |
| `slot` (601) | 348 | 3,828 | 11.0 |
| tamper guard (0..11) | — | 3 | — |

37,412 calls total, which is exactly half the 74,824 `adjust-rel-base`
executions — every call is one `REL_BASE +=` in and one out, with no
exceptions, no tail calls, and no leaks. Two rows are worth pausing on.
`draw` is called 19,456 times but 20,456 draw commands reach the wire: the
missing 1,000 are the initial repaint, which emits inline instead of calling
`draw` — the two display paths, counted. And `tile_at`'s 16,912 calls are
1,000 (repaint) + 15,912 (physics), i.e. **3.33 probes per tick** against the
three the code shows, the excess being the ticks where a bounce sent control
back to 161 to re-probe.

**Two numbers that look different elsewhere and aren't.** The
[summary table](summary_2019.md) records 609,973 `vm-step!` calls and 20,805
draw commands for the same run. `605,195 + 4,778 = 609,973` — the disassembler
counts completed instructions, `vm-step!` counts calls, and a blocked read is
a call that completes no instruction. `20,456 + 349 = 20,805` — the summary
counts every output triple, the disassembler separates the score sentinels
from the tile draws.

## What changes between users' inputs

AoC generates a different program per user, so the honest test of everything
above is whether it survives an input it was never written against. A second
user's Day 13 program, run through the same passes:

| | this repo's input | the second input |
|---|---:|---:|
| program length | 2,640 cells | 2,800 cells |
| screen | 40 × 25 | **45 × 24** |
| blocks (`mem[387]`) | 348 | 462 |
| screen array | 639 … 1638 | 639 … 1718 |
| point-value array | 1639 … 2638 | 1719 … 2798 |
| hash | `((25x + y)·503 + 366) mod 1000` | `((24x + y)·547 + 67) mod 1080` |
| canary | `mem[2639] == 310356` | `mem[2799] == 144351` |
| ball / paddle start | (18,20), paddle 20 | (20,19), paddle 22 |
| paddle row / lose line | 23 / 24 | 22 / 23 |
| Part 1 / Part 2 | 348 / 16999 | **462 / 23981** |

**The whole memory map is a function of `(W, H)`.** Length is
`639 + 2·W·H + 1`; the table base is `639 + W·H`; the modulus is `W·H`; the
column multiplier is `H`; the paddle sits on row `H − 2` and the lose line is
`H − 1`; the paddle clamp is `1 < x < W − 2`. Every one of those relations
holds on both inputs, which is a much stronger statement than "the constants
differ" — the generator is parameterised by the board size and nothing else
structural.

**The code region is 639 cells in both**, and every instruction sits at the
same address in both. That is why the array base is `639` for everyone. But
**148 of those 639 cells differ**, which is the template randomisation
[named above](#the-idiom-set) caught in the act:

```
addr 22   mine: 20102  1  382  1     rel[1] = #1 * mem[382]
          alt : 21001  382  0   1     rel[1] = mem[382] + #0
addr 615  mine: 21101  366  0   3     rel[3] = #366 + #0
          alt : 21102  1  67   3      rel[3] = #1 * #67
```

Same instruction, same width, same address, different template — so addresses
never move, but **which operand slot holds a constant does**. That distinction
cost this disassembler a bug: reading the hash addend from a fixed cell (616)
gives `366` on one input and `1` on the other, silently. The fix is to decode
the instruction and take its immediate operand — preferring the one that isn't
the operation's identity element when both are immediate, which is exactly
what makes the two templates equivalent. `d13-imm` in
[scripts/intcode_disasm.rkt](../../scripts/intcode_disasm.rkt) does that now,
and the tool reproduces the table above on both inputs unaided.

**The static solve generalises.** Reading the second input's screen array gives
462 blocks; summing its point table over those cells through its *own* recovered
hash gives 23981. Both match what the cabinet reports when you actually play it
(6,177 ticks, board cleared). The disassembly is a description of the
*generator*, not of one file.

One footnote, because it is the guard doing precisely the job
[named at the top](#the-head-0--11--a-tamper-guard-that-is-really-a-parser-self-test):
that second input arrived as 2,800 pasted integers, and the first thing that
confirmed the transcription was correct was the program's own canary — cell
2,799 still holding 144351. A parser self-test, used as one.

## The problem within the problem

Every previous Intcode disassembly ended with the machine winning something:
Day 5's obfuscation forced a dynamic trace, Day 9's calling convention had to
be inferred, Day 11's interactive input made the trace and the solve the same
computation. Day 13 inverts it. **The program is well-structured enough that
reading it beats running it.**

The cabinet is a data structure with an interpreter wrapped around it. Once
the disassembly names the two arrays — the screen at 639, the point values at
1639 behind an affine permutation — Part 1 is a `count` and Part 2 is a `sum`,
both over 1,000 integers already sitting in the file. 605,195 executed
instructions, 4,778 simulated ticks, and a controller with a correctness proof
compute the same `16999` that a two-line fold computes without starting the
VM at all.

That is not an argument for shipping the static solve. [`src/day13.rkt`](../../src/day13.rkt)
plays the game, and it should: the static shortcut depends on the layout
constants of *this* input's build of the generator (base 639, multiplier 503,
modulus 1000, the `25*x + y` transposition), and one of those changing turns a
correct program into a wrong one silently. The puzzle's contract is the output
protocol, not the memory map.

What the shortcut *is* good for is the thing this repo keeps coming back to:
knowing which of two computations you're actually doing. Playing Breakout to
find `16999` looks like a simulation problem, and the
[function guide](day13_function_guide.md) treats it as one — control theory,
bang-bang tracking, a parity argument for why greedy is optimal. The
disassembly says the simulation was never load-bearing. Every one of those
4,778 ticks was recomputing the same commutative sum in a very expensive
order, and the only decision the player ever makes is binary: finish the game,
or drop the ball and score nothing.
