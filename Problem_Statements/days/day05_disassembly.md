# Day 5 — Disassembling the TEST diagnostic program

> The [function guide](day05_function_guide.md) builds the Day 5 Intcode VM
> and notes in passing that the puzzle input is "a self-test suite written
> in Intcode." This file *proves* that by taking the input apart the way
> you'd reverse an unknown binary — and discovers something the Day 2
> disassembly's "Caveats and Day 5" section didn't even anticipate: the
> program is **self-modifying**, so static disassembly is defeated and only
> *dynamic* (executing) disassembly is faithful. The payoff is a clean
> reveal of how the program works: a single polymorphic instruction whose
> opcode is computed from your input routes system-ID 1 and system-ID 5 down
> two completely different test batteries.

## What we're disassembling

The puzzle input is 678 integers. On [Day 2](day02_disassembly.md) the
analogous program was 145 integers of branchless straight-line code that a
**linear sweep** disassembled completely. Day 5 has three new wrinkles that
each break a disassembly assumption:

1. **Parameter modes** — an operand can be a literal (`#5`) or an address
   (`mem[5]`), so the decoder must read the mode digits before it can print
   an operand.
2. **Jumps** — the next instruction is no longer `ip + width`; control flow
   forks, so address order stops matching execution order.
3. **Self-modification** — instructions *write into cells that are later
   executed as code*, so the bytes on disk are not the instructions that run.

The first two are what the Day 2 file predicted. The third is the surprise,
and it's the one that matters.

---

## Pass 1 — Static recursive descent (and why it fails)

The standard answer to "jumps break the linear sweep" is **recursive-descent
disassembly**: start at the entry point and *follow control flow* — decode
an instruction, then recurse into its successors (the fall-through, plus a
jump's target when that target is a static immediate). Only cells reachable
as code get decoded; everything else is data. Here is the entire result of
following control flow from address 0:

```
addr | raw                      | operation
-----+--------------------------+-------------------------------------
   0 | 3 225                    | mem[225] = INPUT
   2 | 1 225 6 6                | mem[6] = mem[225] + mem[6]
   6 | 1100                     | ??? raw=1100
   7 | …                        | data: 1, 238, 225, 104, 0, … (671 data cells)
```

It dies after **two real instructions** (the third row, at address 6, is
already garbage). Address 6 holds `1100`, whose low two digits are `00` —
not a valid opcode — so the disassembler gives up and calls the remaining
671 cells "data." That looks like a bug in the disassembler. It isn't. Look
at the instruction at address 2:

```
mem[6] = mem[225] + mem[6]
```

It **writes to address 6** — the very cell the processor will execute next
(instruction 2 is four cells wide, so after it `ip` becomes 6). And it
writes there *before* control reaches 6. So the `1100` on disk is never
executed; what executes is `mem[225] + 1100`, a value that doesn't exist
until runtime. This is **self-modifying code**, and it is fatal to *any*
static analysis: you cannot disassemble instructions that don't exist until
the program builds them.

---

## The trick: address 6 is a polymorphic instruction

This is the whole obfuscation, and it's worth seeing in full. Address 0
reads your system-ID input into `mem[225]`. Address 2 then computes:

```
mem[6]  :=  mem[225] + mem[6]  =  input + 1100
```

Because `1100 mod 100 == 0`, the opcode of the rebuilt instruction at
address 6 is *exactly your input*:

| input | `mem[6]` becomes | decodes as | effect |
|------:|-----------------:|------------|--------|
| `1`   | `1101`           | opcode **01 = add**, modes `11` (both immediate): `1101,1,238,225` | `mem[225] = 1 + 238` — fall through into the **arithmetic** tests |
| `5`   | `1105`           | opcode **05 = jump-if-true**, modes `11`: `1105,1,238` | `1 != 0`, so **jump to 238** — into the **comparison/jump** tests |

One cell, two entirely different instructions, selected by adding the input
to a constant. System-ID `1` (air conditioner) falls straight through into
the block that tests *arithmetic and parameter modes*; system-ID `5`
(thermal radiator) jumps into the block that tests *comparisons and jumps*.
The program is a **dispatcher disguised as data**, and the dispatch key is
folded into an opcode by arithmetic. No static disassembler can see this,
because the branch target and the opcode are both *computed*.

## Pass 2 — Dynamic disassembly (executing the program)

The faithful disassembly is to **run** the program and decode each
instruction against *live* memory as it executes — self-modification simply
resolves itself, because by the time `ip` reaches a modified cell the write
has already happened. The script's `trace-exec` does exactly this for both
inputs:

```
=== DYNAMIC TRACE — input 1 ===
61 instructions executed.
outputs (10): (0 0 0 0 0 0 0 0 0 6731945)

    33  add (1)
    17  mul (2)
     1  in (3)
    10  out (4)
  comparisons (less-than + equals): 0
  jumps       (jit + jif):          0

=== DYNAMIC TRACE — input 5 ===
101 instructions executed.
outputs (1): (9571668)

    14  add (1)
    24  mul (2)
     1  in (3)
     1  out (4)
    20  jump-if-true (5)
    17  jump-if-false (6)
    12  less-than (7)
    12  equals (8)
  comparisons (less-than + equals): 24
  jumps       (jit + jif):          37
```

The two histograms are the proof. They are **disjoint in exactly the
features each system-ID is supposed to test**:

- **Input 1** runs **61 instructions with zero comparisons and zero jumps** —
  pure `add`/`mul`/`out`, straight-line self-modifying code. It emits **ten**
  outputs: nine `0`s (each "this arithmetic/parameter-mode test passed") and
  the diagnostic code `6731945`. This is the air-conditioner path: it
  validates the parts of the VM that existed in spirit on Day 2 (arithmetic,
  now with modes).
- **Input 5** runs **101 instructions including 12 `less-than`, 12 `equals`,
  and 37 jumps** — and emits a *single* output, the diagnostic code
  `9571668`. The twelve-and-twelve is not a coincidence: it exercises the
  two comparison opcodes across position/immediate operand combinations and
  uses jumps to skip past a failure-output unless a test passes. This is the
  thermal-radiator path: it validates the *new* control-flow machinery Day 5
  added.

---

## The problem within the problem: it's a per-subsystem test selector

Put the two passes together and the design is clear. The TEST diagnostic is
a **unit-test suite for your own interpreter**, and the system-ID input is
the *test selector*:

- `mem[6] = input + 1100` turns the input into an opcode, so the input
  literally chooses which instruction runs at address 6;
- system-ID `1` → fall through → the **arithmetic + parameter-mode** test
  battery (add/mul/immediate/position), each emitting `0` on success;
- system-ID `5` → jump → the **comparison + jump** test battery (the exact
  opcodes `5`/`6`/`7`/`8` you implemented for Part 2), emitting only the
  final code on success.

That is why Part 1 and Part 2 of the puzzle ask you to feed `1` and `5`:
they are running *different halves of the test suite*, and Part 2's half is
precisely the half that needs the opcodes Part 2 told you to add. The
function guide's `(andmap zero? (drop-right outs 1))` assertion is checking
the suite's own contract — *every test before the diagnostic code reports
success* — and the disassembly shows what those tests physically are.

### Corollary: the Part 1 / Part 2 split *is* the opcode split

The input-1 histogram has a sharp consequence: it contains **no opcodes
`5`–`8` at all**. So Part 1 is solvable by an interpreter that doesn't even
*implement* jumps and comparisons — only `1`/`2`/`3`/`4`/`99` plus parameter
modes. The two halves of the puzzle map exactly onto two halves of the
instruction set:

| | Opcodes exercised | Features under test |
|---|---|---|
| **Part 1** (input `1`) | `1 2 3 4 99` + modes | arithmetic, I/O, immediate vs position |
| **Part 2** (input `5`) | the above **+ `5 6 7 8`** | jumps + comparisons |

This is not a guess — strip opcodes `5`–`8` out of the interpreter entirely
(make them raise) and run both inputs:

```
Part 1 with a 1/2/3/4/99-only interpreter: 6731945     ; correct
input 5 with the same interpreter:         error — hit opcode 5 at address 6
```

Part 1 still produces the right answer; input 5 dies *immediately*, and it
dies at **address 6** — the polymorphic dispatch cell from the previous
section. Seen from this side, address 6 is the exact boundary between "Part
1 needs nothing past Day 2 + modes + I/O" and "Part 2 needs control flow":
the first instruction system-ID 5 reaches that system-ID 1 never does is the
opcode-5 jump that cell becomes (`5 + 1100 = 1105`).

The staging is deliberate on AoC's part — Part 1's prose introduces modes
and I/O; Part 2's prose introduces jumps and compares — and the input
*enforces* it. A subtle trap falls out: if you implemented only through Part
1, your jump/compare opcodes would be completely **untested**, because the
air-conditioner path never executes one. Part 2's input `5` is what forces
those opcodes to run, which is the whole point of a diagnostic that selects
its battery by input.

## The disassembly-theory connections

The three passes correspond to the three classical disassembly strategies,
and Day 5 is a compact demonstration of why each exists:

- **Linear sweep** (Day 2): decode `ip += width` from the top. Correct only
  for branchless, non-self-modifying basic blocks. Day 5 breaks it at the
  first jump *and* the first self-write.
- **Recursive descent** (this file, Pass 1): follow control flow from the
  entry, decoding both branch targets. The textbook answer to jumps — and
  still **defeated by self-modifying code**, because the instructions it
  would decode don't exist on disk. This is a real limitation of static
  analysis, not an artifact of a toy implementation: it is the same reason
  production static disassemblers (IDA, Ghidra) carry explicit
  "self-modifying / packed code" caveats and fall back to emulation.
- **Dynamic / trace disassembly** (Pass 2): execute and log. Always faithful
  to what actually runs, at the cost of only covering the path a *given
  input* takes (hence we trace both `1` and `5`). This is the technique
  behind dynamic binary instrumentation (Pin, DynamoRIO) and the only
  correct lens on packed or self-modifying binaries.

The **self-modifying-code** twist also has a name in the malware-analysis
literature: an opcode synthesized at runtime from data is a tiny **packer /
decryptor stub**, and "the real instruction only exists after the stub
runs" is exactly why such samples must be *run* (in a sandbox) to be
understood. AoC's generator is doing a benign version of the same thing to
make the input resist a `grep`-and-eyeball read.

The **clox parallel:** a linear sweep is what a naïve bytecode printer does
to a `Chunk`; recursive descent is what you'd need once `OP_JUMP`/
`OP_LOOP` enter; and dynamic tracing is what your VM's debug
`disassembleInstruction`-in-the-run-loop already does — print each
instruction *as the interpreter dispatches it*. Day 5's input forces the
third because it rewrites its own bytecode, something clox never does but a
self-hosting or JIT-ing VM absolutely can.

## Caveats and Days 7 / 9

This dynamic tracer generalizes cleanly to the rest of the Intcode trilogy,
with two additions the later days force:

- **Input queues (Day 7).** `trace-exec` takes a single `input` value
  because the TEST program reads input once. [Day 7](day07_function_guide.md)
  feeds a *stream* of inputs; the script's `trace-exec/inputs` and
  `run-day7-disasm` handle this — see [day07_disassembly.md](day07_disassembly.md).
- **Relative mode + relative base (Day 9).** A third parameter mode (`2`)
  and a movable base register join `param-mode`; the decoder gains a
  `rel[k]` operand rendering and the executor a `base` accumulator. The
  histogram-and-trace structure is unchanged. Done in
  [day09_disassembly.md](day09_disassembly.md), where — unlike here — static
  recursive descent *succeeds* (BOOST isn't self-modifying), and the relative
  base turns out to be a **stack frame pointer** driving a recursive subroutine.

What does *not* generalize is the affine symbolic proof from
[Day 2](day02_disassembly.md): the moment a program branches on a
data-dependent value, its output stops being a single affine form, which is
why this file skips that pass. Day 2's closed form was a luxury of
branchless code; Day 5 spends that luxury on its first jump.
